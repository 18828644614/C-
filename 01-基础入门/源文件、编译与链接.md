# 源文件、编译与链接

## 学习目标

- [ ] 说出源文件、头文件、目标文件和可执行文件分别是什么。
- [ ] 描述预处理、编译、汇编、链接和运行各自的职责。
- [ ] 在 Windows 上使用 MSVC 或 MinGW-w64 编译一个 C++ 程序。
- [ ] 区分编译错误、链接错误和运行时错误，并知道从哪里开始排查。

## 1. 从代码到程序：先建立全景图

C++ 源代码不是直接被 CPU 执行的。编译器工具链会把人类可读的 .cpp 文件逐步变成操作系统能够启动的可执行文件：

~~~text
main.cpp、其他 .cpp、头文件
              │
              ▼
       预处理（展开 #include、宏）
              │
              ▼
       编译（检查 C++ 语法和类型）
              │
              ▼
       汇编（生成 .obj / .o 目标文件）
              │
              ├── 其他目标文件、静态库、动态库
              ▼
       链接（解决跨文件的函数和变量引用）
              │
              ▼
       .exe（Windows）或可执行文件（Linux/macOS）
              │
              ▼
       运行
~~~

可以把它类比成出版一本书：.cpp 是分别写好的章节，预处理像把引用的资料复制进来，编译像检查每一章的语法，汇编像排版成印刷版页面，链接则把所有章节和库装订成一本可以发行的书。某一步失败，后面的步骤就不会正常完成。

### 文件的角色

| 文件 | 作用 | 常见后缀（Windows） |
| --- | --- | --- |
| 源文件 | 写函数和类的具体实现；每个源文件会单独处理 | .cpp |
| 头文件 | 放声明、类型定义和模板，供多个源文件包含 | .h、.hpp |
| 目标文件 | 一个源文件编译、汇编后的中间结果，尚未成为完整程序 | .obj（MSVC）、.o（MinGW） |
| 静态库 | 一组已经编译好的目标代码，链接时复制进程序 | .lib、.a |
| 动态库 | 运行时加载的共享代码 | .dll（通常还需要 .lib 导入库） |
| 可执行文件 | 链接完成后可以启动的程序 | .exe |

> 初学阶段可以把“编译”当作整个构建过程的口语说法；严格来说，编译只是其中一个阶段，完整过程还包括预处理、汇编和链接。

## 2. 源文件、头文件和编译单元

这一节最容易混淆的地方是：头文件不是一个“单独编译的文件”，#include 也不是像其他语言那样“导入一个已经编译好的模块”。我们用一个很小的程序逐步观察。

### 2.1 先看三个文件各自负责什么

greeting.h：

~~~cpp
#pragma once

#include <string>

// 声明：告诉使用者“这个函数存在，以及如何调用它”
std::string make_greeting(const std::string& name);
~~~

greeting.cpp：

~~~cpp
#include "greeting.h"

// 定义：提供函数真正要执行的代码
std::string make_greeting(const std::string& name) {
    return "你好，" + name + "！";
}
~~~

main.cpp：

~~~cpp
#include <iostream>
#include "greeting.h" // 把 make_greeting 的声明放到这里

int main() {
    std::cout << make_greeting("小明") << '\n';
}
~~~

可以先这样记：

- .h/.hpp 通常放“**别人需要知道的接口**”，也就是声明。
- .cpp 通常放“**程序真正执行的实现**”，也就是定义。
- main.cpp 只需要知道函数的名字、参数和返回类型，就能检查调用是否正确；它不需要在本文件中看到函数体。

这里的“接口”可以理解为使用说明书：调用者需要知道“函数叫什么、要传什么、会返回什么”，不必先阅读函数内部的每一行实现。

### 2.2 #include 实际做了什么

预处理器处理 main.cpp 时，看到：

~~~cpp
#include "greeting.h"
~~~

它会找到这个头文件，并把头文件中的内容**按文本放到这一行的位置附近**，再把得到的整体内容交给编译器。为了突出重点，可以把结果想象成这样（实际还会包含大量标准库内容）：

~~~cpp
// 来自 <iostream> 的内容省略
#include <string>

// 这是 greeting.h 被展开后的内容
std::string make_greeting(const std::string& name);

int main() {
    std::cout << make_greeting("小明") << '\n';
}
~~~

所以，编译 main.cpp 时，编译器看到了 make_greeting 的**声明**，能够检查：

- 函数名是否拼写正确；
- 参数类型是否匹配（这里需要一个 const std::string&）；
- 返回值是否能传给 std::cout。

但此时编译器还没有看到 greeting.cpp 中的函数体。它会先生成 main.obj/main.o，并在其中记下：“这里需要一个名为 make_greeting 的函数，稍后请找到它。”

同样地，处理 greeting.cpp 时，编译器会得到另一个编译单元，其中包含函数的**定义**，并生成 greeting.obj/greeting.o。最后链接器把这两个目标文件放在一起，将 main.obj 中“需要的函数”与 greeting.obj 中“提供的函数”配对，才能生成 .exe。

整个关系可以画成：

~~~text
greeting.h   ──声明────────────────┐
                                   ├─► 预处理/编译 ─► main.obj ─┐
main.cpp     ──include greeting.h─┘                            │
                                                                ├─► 链接 ─► greet.exe
greeting.cpp ──定义────────────────────► 预处理/编译 ─► greeting.obj ─┘
~~~

这也解释了一个常见现象：**main.cpp 可以单独编译成功，但把它单独链接成程序会失败**。因为它知道函数“长什么样”，却还没有函数“真正做什么”的机器码。

### 2.3 什么是编译单元

一个 .cpp 文件经过预处理后，连同它递归包含进来的所有头文件内容，形成一个**编译单元（translation unit）**。上面的程序至少会产生两个编译单元：

1. main.cpp + greeting.h（以及 iostream 等头文件）；
2. greeting.cpp + greeting.h（以及 string 等头文件）。

注意：greeting.h 本身通常不会单独生成一个 greeting.obj。它只是分别被两个 .cpp 展开，所以同一份声明会出现在两个编译单元中。

每个编译单元可以独立检查和编译。修改 greeting.cpp 时，通常只需重新编译它，再重新链接；修改 greeting.h 时，所有包含它的 .cpp 都需要重新编译。

### 2.4 声明和定义到底有什么区别

| 概念  | 初学者可以怎样理解           | 例子                                      |
| --- | ------------------- | --------------------------------------- |
| 声明  | “有这么一个东西，请按这个类型使用它” | int add(int, int);                      |
| 定义  | “把这个东西真正创建出来/实现出来”  | int add(int a, int b) { return a + b; } |

对函数来说，声明通常以分号结束，没有函数体；定义有函数体。下面两行分别承担不同任务：

~~~cpp
// 声明：只有函数签名（名字、参数、返回类型）
int add(int, int);

// 定义：有函数体，提供实际行为
int add(int a, int b) {
    return a + b;
}
~~~

如果只有声明没有定义，编译器通常仍能编译调用代码，但链接器最后会报告 unresolved external symbol 或 undefined reference。如果只有定义却没有让调用者看到声明，调用者在编译阶段就不知道这个函数，可能报告“未声明的标识符”。

> 对变量、类和模板来说，声明/定义还有更多细节；本节先用普通函数建立最重要的直觉。

### 2.5 为什么头文件需要防重复包含

由于 #include 是文本展开，同一个头文件可能被间接包含多次。例如 main.cpp 包含 a.h，而 a.h 和 b.h 都包含 greeting.h。如果头文件里有类定义、结构体定义或其他不应重复出现的内容，展开两次就可能产生重复定义。

最简单的写法是：

~~~cpp
#pragma once // 大多数 Windows 编译器都支持
~~~

也可以使用传统的头文件保护宏：

~~~cpp
#ifndef GREETING_H
#define GREETING_H

std::string make_greeting(const std::string& name);

#endif // GREETING_H
~~~

两种写法的目的相同：**同一个编译单元中，头文件的正文最多展开一次**。#pragma once 简洁，保护宏更传统、可移植性更明确；初学时选一种并保持一致即可。

## 3. 四个构建阶段（以及运行）

把下面这句话记成主线：

> C++ 工具链先把“方便人阅读的源代码”变成“机器指令”，再把分散在多个文件中的机器指令组合起来，最后交给操作系统运行。

以第 4 节中的 hello.cpp 为例，它会经历下面的过程：

| 阶段 | 输入 | 这一阶段做什么 | 主要输出 |
| --- | --- | --- | --- |
| 预处理 | .cpp + 被包含的头文件 | 处理以 # 开头的指令，决定哪些文本保留 | 预处理后的 C++ 文本 |
| 编译 | 预处理后的 C++ 文本 | 理解 C++ 语法和类型，生成低级代码 | 汇编代码（或交给汇编器的结果） |
| 汇编 | 汇编代码 | 把汇编指令编码为机器指令 | .obj（MSVC）或 .o（GCC） |
| 链接 | 多个 .obj/.o、静态库、运行库 | 把跨文件的引用配对，合并成完整程序 | .exe |
| 运行 | .exe 和所需 DLL | 操作系统加载程序并执行 main | 屏幕输出或其他程序行为 |

这几个阶段通常由一条 g++ 或 cl 命令自动连续完成。只有在学习或排错时，我们才会把它们拆开观察。

### 3.1 预处理：先把“指令”处理掉

预处理器只关注以 # 开头的预处理指令，常见工作有三类：

1. 找到并展开 #include 文件；
2. 做简单的宏替换，例如把 APP_NAME 替换成一段文字；
3. 根据 #if、#ifdef 等条件决定某些代码是否保留，同时删除注释。

例如源文件是：

~~~cpp
#include <iostream> // 这条 #include 会在预处理时处理

#define APP_NAME "初学者示例"

int main() {
    std::cout << APP_NAME << '\n'; // APP_NAME 会被替换
}
~~~

为了便于理解，可以把预处理后的关键部分想象成：

~~~cpp
// <iostream> 的大量内容省略
int main() {
    std::cout << "初学者示例" << '\n';
}
~~~

这里的“想象成”很重要：真实结果会非常大，因为 iostream 还会递归包含很多标准库头文件；而且预处理器并不理解 std::cout 的类型，它只是按规则处理文本和条件。

**这一阶段能发现什么？**

- include 指向的文件不存在；
- 宏名称拼错、宏展开结果不符合预期；
- 条件编译把本来需要的代码排除了。

**这一阶段不能保证什么？**

它不会检查完整的 C++ 语法和类型。例如宏替换后产生了不合法的 C++，要到下一步的编译阶段才会报错。

在 MinGW-w64 中可以用下面的命令把结果保存下来：

~~~powershell
g++ -std=c++20 -E hello.cpp -o hello.i
~~~

-E 的意思是“只做预处理，不继续编译和链接”。hello.i 是文本文件，可以用编辑器搜索 APP_NAME，查看它是否已经被替换。

### 3.2 编译：理解 C++，检查规则

编译器接收预处理后的 C++ 文本，真正开始理解 C++ 语言。它会：

1. 分析语法，例如括号和分号是否正确；
2. 查找名字，例如 main、std::cout 是否已声明；
3. 检查类型，例如把字符串、整数传给函数时是否匹配；
4. 把通过检查的代码转换成汇编或等价的低级表示。

例如把分号删掉：

~~~cpp
#include <iostream>

int main() {
    std::cout << "Hello, C++!\n" // 故意缺少分号
    return 0;
}
~~~

编译器通常会在这一阶段报告 expected ';' 或类似的语法错误。因为程序连合法的 C++ 都不是，所以不会继续生成可用于链接的目标文件。

这里要特别注意：编译器通常只处理一个编译单元。它看到 main.cpp 中调用了某个函数，只要已经有正确的声明，就能检查调用方式；函数的真正实现可以在另一个 .cpp 中，稍后由链接器处理。

在 MinGW-w64 中，-c 表示编译并汇编，但暂时不链接：

~~~powershell
g++ -std=c++20 -Wall -Wextra -pedantic -c hello.cpp -o hello.o
~~~

成功后会得到 hello.o。MSVC 对应的选项是 /c，输出通常是 hello.obj：

~~~powershell
cl /std:c++20 /W4 /EHsc /c hello.cpp
~~~

### 3.3 汇编：把低级代码编码成机器指令

编译器生成的汇编代码仍然是人类可以勉强阅读的低级文本，例如“把某个值放入寄存器”“调用某个函数”。汇编器会把这些指令编码成 CPU 能执行的机器字节，并写入目标文件。

目标文件不等于可执行文件。它除了机器码，还包含：

- 符号表：记录本文件提供或需要的函数、变量名称；
- 重定位信息：记录某些地址要等链接器确定；
- 代码段和数据段等布局信息。

因此目标文件可能还写着“这里要调用 make_greeting，但它在另一个目标文件中”。目标文件通常不能直接双击运行。

> 有些编译器会把编译和汇编合并在内部完成，所以初学者平时不一定能看到单独的汇编文件。理解它的作用即可。

### 3.4 链接：把“需要”和“提供”配对

假设有两个目标文件：

~~~text
main.obj    ：需要 make_greeting
greeting.obj：提供 make_greeting
~~~

链接器会完成三件关键事情：

1. 把多个目标文件、静态库和运行库放到一起；
2. 查找每个“未解决的符号”，找到对应的定义；
3. 修正函数调用地址和其他重定位信息，写出最终的 .exe。

如果只执行：

~~~powershell
g++ -std=c++20 -Wall -Wextra -pedantic -c main.cpp -o main.o
g++ main.o -o greet.exe
~~~

第二条命令可能失败，因为 main.o 需要 make_greeting，但命令中没有提供 greeting.o。GCC 常见的错误是 undefined reference；MSVC 常见的错误是 unresolved external symbol。

把实现文件补上：

~~~powershell
g++ main.o greeting.o -o greet.exe
~~~

链接器就能找到函数定义，生成 greet.exe。这个例子说明：

- “编译通过”只表示当前编译单元的 C++ 写法正确；
- “链接通过”才表示组成完整程序所需的符号都找到了；
- 链接命令中漏掉一个 .obj/.o 或库，是链接失败的常见原因。

### 3.5 运行：操作系统真正启动程序

链接得到 greet.exe 后，Windows 还要负责运行它：

1. 找到并加载 .exe；
2. 加载它依赖的 DLL 和运行库；
3. 创建进程，准备栈、堆等内存区域；
4. 执行运行库的启动代码，最终调用 main；
5. main 返回后，运行库整理资源并把退出码交给操作系统。

在 PowerShell 中运行当前目录的程序：

~~~powershell
.\greet.exe
~~~

如果看到“缺少某个 DLL”，说明编译和链接可能已经成功，问题发生在运行阶段。若程序能启动但输出错误或崩溃，则应检查逻辑、越界、空指针和输入数据，并使用调试器定位。

### 3.6 用一句话判断错误属于哪一步

- 看到“找不到头文件”：先检查预处理阶段的文件路径和 include 写法。
- 看到“expected ';'”“类型不匹配”：检查编译阶段的 C++ 语法和类型。
- 看到“undefined reference”“unresolved external symbol”：检查链接命令是否包含实现文件或所需库。
- 程序启动时报 DLL 错误：检查运行阶段的 DLL 搜索路径、位数和运行库。
- 程序启动后崩溃：这是运行逻辑问题，使用调试器，而不是反复修改链接参数。

## 4. Windows 上编译第一个程序

先创建 hello.cpp：

~~~cpp
#include <iostream>

int main() {
    std::cout << "Hello, C++!\n";
    return 0; // 0 通常表示程序正常结束
}
~~~

### 方式 A：Visual Studio / MSVC（推荐使用 Developer PowerShell）

打开“Developer PowerShell for VS”或“x64 Native Tools Command Prompt for VS”，切换到文件所在目录，再执行：

~~~powershell
cl /std:c++20 /W4 /EHsc hello.cpp /Fe:hello.exe
.\hello.exe
~~~

- cl：MSVC 编译器驱动程序。
- /std:c++20：启用 C++20 语言标准（也可以改为项目需要的标准）。
- /W4：开启较严格的警告；警告值得认真阅读。
- /EHsc：启用常规 C++ 异常处理语义。
- /Fe:hello.exe：指定输出文件名。
- PowerShell 执行当前目录的程序要写 .\hello.exe，只写 hello.exe 可能不会被找到。

如果提示“cl 不是内部或外部命令”，通常是打开了普通 PowerShell，而不是 Visual Studio 的开发者终端；也可能是尚未安装“使用 C++ 的桌面开发”工作负载。

### 方式 B：MinGW-w64 / GCC

在已把 MinGW-w64 的 bin 目录加入 PATH 的 PowerShell 中执行：

~~~powershell
g++ -std=c++20 -Wall -Wextra -pedantic hello.cpp -o hello.exe
.\hello.exe
~~~

-Wall 和 -Wextra 打开常用警告，-pedantic 提醒不符合标准的写法，-o 指定输出文件。若提示“g++ 不是内部或外部命令”，请检查 MinGW-w64 安装和 PATH，然后重新打开终端。

### 拆开每一步（用于理解）

平时使用一条命令即可；下面的命令用于观察中间文件：

~~~powershell
# GCC/MinGW：只预处理，输出到 hello.i
g++ -std=c++20 -E hello.cpp -o hello.i

# GCC/MinGW：只编译和汇编，不链接，生成 hello.o
g++ -std=c++20 -Wall -c hello.cpp -o hello.o

# GCC/MinGW：链接目标文件，生成 hello.exe
g++ hello.o -o hello.exe
~~~

MSVC 的对应观察命令如下（选做）：

~~~powershell
# 只预处理，生成 hello.i
cl /P hello.cpp

# 只编译和汇编，生成 hello.obj
cl /std:c++20 /W4 /EHsc /c hello.cpp

# 链接目标文件
link hello.obj /OUT:hello.exe
~~~

## 5. 多文件示例：声明、定义和链接

把下面三个文件放在同一个目录。

greeting.h：

~~~cpp
#pragma once // 防止同一个编译单元重复包含此头文件

#include <string>

// 这里只是声明：实现放在 greeting.cpp
std::string make_greeting(const std::string& name);
~~~

greeting.cpp：

~~~cpp
#include "greeting.h"

// 这是 make_greeting 的唯一一个定义
std::string make_greeting(const std::string& name) {
    return "你好，" + name + "！";
}
~~~

main.cpp：

~~~cpp
#include <iostream>
#include "greeting.h" // 编译时看到声明，知道怎样调用函数

int main() {
    std::cout << make_greeting("小明") << '\n';
}
~~~

MSVC（Developer PowerShell）：

~~~powershell
# /c 表示只生成目标文件，不进行链接
cl /std:c++20 /W4 /EHsc /c greeting.cpp main.cpp

# 把两个 .obj 链接成一个 .exe
cl greeting.obj main.obj /Fe:greet.exe
.\greet.exe
~~~

MinGW-w64：

~~~powershell
g++ -std=c++20 -Wall -Wextra -pedantic -c greeting.cpp -o greeting.o
g++ -std=c++20 -Wall -Wextra -pedantic -c main.cpp -o main.o
g++ greeting.o main.o -o greet.exe
.\greet.exe
~~~

这里 main.cpp 能通过编译，是因为头文件提供了声明；最终能通过链接，是因为 greeting.cpp 提供了定义。若忘记把 greeting.cpp 放入链接命令，常见结果就是链接错误，而不是编译错误。

## 6. 常见错误：先看错误发生在哪一步

| 现象 | 通常发生的阶段 | 例子与排查方向 |
| --- | --- | --- |
| fatal error C1083、No such file or directory | 预处理/编译 | 头文件名拼错、当前目录或 -I（GCC）/I（MSVC）搜索路径不对 |
| expected ';'、类型不匹配 | 编译 | 检查报错行附近的语法、拼写和类型 |
| unresolved external symbol、undefined reference | 链接 | 只有声明没有定义，或漏掉了某个 .obj/.o/库 |
| multiple definition、重复符号 | 链接 | 把非 inline 的函数实现直接写进了被多处包含的头文件 |
| 程序启动时报缺少 DLL | 运行 | DLL 不在程序目录或 PATH 中，确认位数和运行库匹配 |
| 程序运行后崩溃或输出错误 | 运行 | 使用调试器检查逻辑、越界、空指针和输入数据 |

排查时先看**第一条错误**，后面的错误可能只是连带结果。不要把所有问题都称为“编译错误”：准确判断阶段，才能快速找到正确的文件和命令。

## 7. 警告、调试版与发布版

- 始终打开警告：MSVC 可从 /W3 或 /W4 开始，GCC/MinGW 可使用 -Wall -Wextra -pedantic。
- 调试版通常保留调试符号、优化较少，便于断点和观察变量。MSVC 常见组合是 /Zi 加较低优化；GCC/MinGW 常见是 -g -O0。
- 发布版通常开启优化，例如 MSVC /O2、GCC -O2。优化可能改变代码执行顺序和变量显示方式，因此排查问题时先用调试配置。
- 修改头文件后，所有包含它的 .cpp 都需要重新编译；只修改某个 .cpp 时，通常只需重新编译该文件，然后重新链接。

## 8. 项目变大后：用 CMake 记住构建规则

手写多条命令适合学习阶段；项目文件增多后，建议让 CMake 生成构建文件。最小示例 CMakeLists.txt：

~~~cmake
cmake_minimum_required(VERSION 3.20)
project(Greeting LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 20)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

add_executable(greet main.cpp greeting.cpp)
~~~

如果使用 Visual Studio 生成器，可以明确指定生成器，这样 Debug 输出路径是确定的：

~~~powershell
cmake -S . -B build-msvc -G "Visual Studio 17 2022"
cmake --build build-msvc --config Debug
.\build-msvc\Debug\greet.exe
~~~

如果使用 MinGW-w64，则可以使用对应的生成器：

~~~powershell
cmake -S . -B build-mingw -G "MinGW Makefiles"
cmake --build build-mingw
.\build-mingw\greet.exe
~~~

-S . 指定源代码目录，-B build-* 指定独立的构建目录。不同生成器的输出路径可能略有区别；如果找不到 .exe，请查看对应的 build 目录。CMake 负责记录源文件、头文件依赖和编译选项，但底层仍然是“编译每个源文件，再链接目标文件”。

## 示例与实践

1. **单文件练习**：给 hello.cpp 增加一个 square(int) 函数，分别用 cl 和 g++ 编译，并保留警告选项。
2. **多文件练习**：把 make_greeting 改成返回包含命令行参数的问候语；故意不链接 greeting.cpp，观察并记录链接器报错，再补上目标文件。
3. **阶段判断**：故意写出一个缺少分号的版本、一个只有声明没有定义的版本，分别判断它们属于编译错误还是链接错误。
4. **观察中间文件**：使用 g++ -E 和 g++ -c 生成 .i、.o，尝试用文本编辑器查看它们，并说明为什么目标文件不是普通文本。
