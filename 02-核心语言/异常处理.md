# 异常处理

## 学习目标
- [ ] 理解异常要解决的问题，以及 `try`、`throw`、`catch` 的基本职责。
- [ ] 能够读懂异常从抛出点向调用者传播，以及传播过程中的栈展开。
- [ ] 使用标准异常类型和自定义异常表达错误，并在合适的位置恢复或终止操作。
- [ ] 正确编写捕获顺序、按 `const` 引用捕获、重新抛出和兜底处理。
- [ ] 理解 RAII 为什么能在异常路径上释放资源，避免内存、文件和锁泄漏。
- [ ] 区分基本保证、强保证和不抛保证，初步设计具有异常安全性的函数。
- [ ] 理解 `noexcept` 的语义，以及析构函数和异常传播之间的关系。
- [ ] 在 Windows 的 MSVC 或 MinGW-w64 环境中编译并运行本章示例。

## 要点

### 1. 为什么需要异常处理

程序运行时可能遇到很多不能由当前语句正常完成的情况：文件打不开、输入格式不正确、内存分配失败、网络连接断开或某个函数的前置条件不满足。C++ 处理这类问题主要有两种思路：

- **返回值或输出参数**：函数返回一个状态码，调用者检查它，再决定下一步做什么。
- **异常（exception）**：函数在发现错误时抛出异常对象，把“错误发生后的处理”交给调用链中更适合处理它的地方。

返回值适合表示调用者预期会经常遇到的结果，例如“查找是否成功”或“用户输入是否有效”。异常适合表示当前函数无法继续完成职责、而且错误处理会打断正常流程的情况。异常不是“更高级的返回值”，它会改变控制流，并启动一套专门的传播和清理机制。

例如，下面两个函数都处理除数为零，但表达的接口意图不同：

~~~cpp
#include <stdexcept>

// 方式一：零除数是调用者需要经常判断的正常分支
bool try_divide(double a, double b, double& result) {
    if (b == 0.0) {
        return false;
    }
    result = a / b;
    return true;
}

// 方式二：零除数意味着本次操作无法完成，交给上层处理
double divide_or_throw(double a, double b) {
    if (b == 0.0) {
        throw std::invalid_argument("除数不能为零");
    }
    return a / b;
}
~~~

两种方式都可以正确。选择时要考虑接口的整体风格：如果函数的大多数调用都需要立刻判断失败，返回 `bool`、`std::optional`、`std::error_code` 或 C++23 的 `std::expected` 往往更直观；如果错误需要跨越多层调用才能由统一入口处理，异常可以避免每一层都手动传递错误码。

异常也不能代替所有错误处理：

1. 用户输入错误通常是可预期的，应提示用户并允许重新输入，而不是让程序直接崩溃。
2. 能在当前层修正的问题，应尽早修正或返回明确结果。
3. 断言、未定义行为和逻辑错误不能靠 `try`/`catch` 修复。越界访问等未定义行为发生后，程序状态可能已经不可信。
4. 不要把异常当作普通循环控制工具。频繁用 `throw` 跳出正常循环会降低可读性，也可能增加运行时成本。

### 2. `try`、`throw` 和 `catch`：异常的三个基本部件

一个最小的异常处理结构如下：

~~~cpp
try {
    // 可能抛出异常的代码
    do_something();
} catch (const std::exception& error) {
    // 处理继承自 std::exception 的异常
    std::cerr << error.what() << '\n';
}
~~~

这三个关键字的职责不同：

| 关键字 | 作用 |
| --- | --- |
| `try` | 标记一段需要监控异常的代码。它本身不会捕获异常。 |
| `throw` | 抛出一个异常对象，立即改变当前控制流。抛出点后面的语句不会继续执行。 |
| `catch` | 声明能处理哪一种异常，并执行对应的处理代码。 |

`throw` 是一个表达式，可以抛出标准异常、自定义异常或其他类型的对象。虽然语法上可以抛出整数、字符串等类型，但工程代码应优先抛出继承自 `std::exception` 的类型，这样调用者可以统一使用 `what()` 获取说明：

~~~cpp
#include <stdexcept>

double divide(double a, double b) {
    if (b == 0.0) {
        throw std::invalid_argument("除数不能为零");
    }
    return a / b;
}
~~~

调用者用 `try` 包住调用，用 `catch` 处理失败：

~~~cpp
#include <iostream>
#include <stdexcept>

int main() {
    try {
        std::cout << divide(10.0, 2.0) << '\n';
        std::cout << divide(10.0, 0.0) << '\n';
        std::cout << "这一行不会执行\n";
    } catch (const std::invalid_argument& error) {
        std::cerr << "计算失败：" << error.what() << '\n';
    }

    // catch 执行完后，程序从整个 try-catch 结构之后继续
    std::cout << "程序仍然可以继续\n";
}
~~~

需要注意：`catch` 只能紧跟在 `try` 代码块后面，一个 `try` 可以有多个 `catch`。如果 `try` 中没有异常，所有 `catch` 都会跳过；如果发生异常，则只执行第一个匹配的处理器。

#### 2.1 为什么通常按 `const` 引用捕获

初学者最推荐的形式是：

~~~cpp
catch (const std::exception& error) {
    std::cerr << error.what() << '\n';
}
~~~

这里有三个目的：

- `const` 表示处理错误时不修改异常对象。
- 引用避免再次复制异常对象，尤其是自定义异常中包含较长消息或其他数据时。
- 以基类引用捕获，可以处理所有继承自 `std::exception` 的标准异常和自定义异常，同时保留多态行为。

按值捕获也可能编译，但捕获派生异常到基类对象时会发生切片，派生类额外信息会丢失：

~~~cpp
catch (std::exception error) { /* 不推荐：可能切片，还会复制 */ }
catch (const std::exception& error) { /* 推荐 */ }
~~~

不要为了“延长生命周期”而捕获指向临时异常对象的裸指针。通常直接按 `const` 引用捕获即可。

#### 2.2 多个 `catch` 的匹配顺序

处理器从上到下检查，**更具体的派生类型必须写在更一般的基类类型前面**：

~~~cpp
try {
    read_configuration();
} catch (const std::invalid_argument& error) {
    // 处理参数格式错误
    std::cerr << "参数错误：" << error.what() << '\n';
} catch (const std::runtime_error& error) {
    // 处理运行过程中发现的其他错误
    std::cerr << "运行时错误：" << error.what() << '\n';
} catch (const std::exception& error) {
    // 处理其他标准异常
    std::cerr << "标准异常：" << error.what() << '\n';
}
~~~

`std::invalid_argument` 继承自 `std::logic_error`，而 `std::logic_error` 和 `std::runtime_error` 都继承自 `std::exception`。如果把 `catch (const std::exception&)` 放在最前面，后面的处理器就永远不会执行，编译器通常会给出“处理器不可达”的警告。

#### 2.3 `catch (...)`：最后的兜底处理器

`catch (...)` 可以匹配任何类型的异常，包括不是 `std::exception` 派生类的异常：

~~~cpp
try {
    third_party_function();
} catch (...) {
    // 这里只知道“发生了某种异常”，拿不到具体消息
    std::cerr << "发生了无法识别的异常\n";
    throw; // 记录后继续向上抛出；如果这里能恢复，也可以不抛
}
~~~

它通常应该放在最后。不要无条件捕获后什么都不做，否则会把真正的错误静默吞掉，使排查变得困难。如果兜底处理器处在程序最外层，记录日志后是否退出，应由程序的恢复能力决定；不能假装程序仍然处于可靠状态。

### 3. 异常如何传播：从抛出点走向处理点

异常处理的一个重要价值是：发现错误的函数不必处理所有错误。假设调用关系如下：

```text
main -> load_config -> parse_port
```

`parse_port` 发现字符串不是合法端口时可以抛出异常；如果它没有本地 `try`，异常会返回到 `load_config`。`load_config` 也没有合适的处理器时，异常继续返回到 `main`。第一个匹配的 `catch` 负责处理它。

传播过程可以概括为：

1. 执行 `throw`，创建或初始化异常对象，并离开当前执行路径。
2. 在当前函数中寻找可匹配的 `catch`；如果当前函数没有合适的处理器，就向调用者返回。
3. 对离开作用域的自动对象执行析构函数，这一步叫**栈展开（stack unwinding）**。
4. 找到匹配的处理器后，执行它；处理器结束后，程序从对应 `try-catch` 结构之后继续。
5. 如果一直传播到线程入口仍没有匹配的处理器，会调用 `std::terminate()`，程序通常会异常终止。

“异常会自动清理资源”这句话并不完整。栈展开只会调用已经构造完成的自动对象的析构函数；裸指针、裸 `HANDLE`、手动 `new` 出来的对象和其他没有 RAII 所有者的资源不会凭空被释放。应让 `std::string`、`std::vector`、`std::unique_ptr`、`std::ofstream`、`std::lock_guard` 或自定义 RAII 类型拥有资源，详见[[对象生命周期与RAII]]。

还有两个容易忽略的边界：

- 异常只能在同一线程的调用链中传播。一个线程函数抛出的异常不会自动被另一个线程的 `try` 捕获；线程入口应自行捕获，或通过 `std::promise`/`std::future` 等机制传递结果。
- `return`、`break` 和异常都可能离开作用域，但只有异常会触发异常处理器；三者都会触发已经构造完成的局部 RAII 对象析构。

### 4. 栈展开与对象生命周期

看下面的完整过程：

~~~cpp
#include <iostream>
#include <stdexcept>

class ScopeLog {
public:
    explicit ScopeLog(const char* name) : name_(name) {
        std::cout << name_ << " 构造\n";
    }

    ~ScopeLog() noexcept {
        std::cout << name_ << " 析构\n";
    }

private:
    const char* name_;
};

void inner() {
    ScopeLog local("inner 的局部对象");
    throw std::runtime_error("inner 失败");
    // 这一行之后的代码不会执行
}

void outer() {
    ScopeLog local("outer 的局部对象");
    inner();
    // inner 抛出异常后，这里也不会继续执行
}

int main() {
    try {
        outer();
    } catch (const std::exception& error) {
        std::cout << "捕获到异常：" << error.what() << '\n';
    }
}
~~~

执行 `inner()` 时，`inner` 的局部对象先析构；异常继续离开 `outer` 时，`outer` 的局部对象再析构；最后 `main` 的 `catch` 处理异常。输出中的析构顺序正是异常栈展开的可观察结果。

如果在构造一个对象的过程中抛出异常，该对象本身没有构造完成，因此不会调用它自身的析构函数；但已经成功构造的成员和基类子对象会被销毁。这也是“在构造函数中尽早把资源交给 RAII 成员”很重要的原因。不要把资源先保存为裸指针，再期待外层对象的析构函数一定能清理半成品。

### 5. 标准异常和自定义异常

标准库在 `<stdexcept>` 和其他头文件中提供了常用异常类型。它们表达的重点不同，选择能让调用者更容易作出处理决策：

| 异常类型 | 适合表达的情况 |
| --- | --- |
| `std::invalid_argument` | 参数类型或格式不符合要求，例如把字母当作端口号。 |
| `std::out_of_range` | 参数或索引超出允许范围；`vector::at()` 越界时会抛出它。 |
| `std::domain_error` | 数学或业务定义域错误，例如对不允许的输入求某种结果。 |
| `std::logic_error` | 调用方违反了可以在逻辑上避免的前置条件；它是多个逻辑错误异常的基类。 |
| `std::runtime_error` | 运行环境导致的失败，例如文件、网络或设备暂时不可用。 |
| `std::system_error` | 带有系统错误码的失败，适合包装操作系统或库的错误。 |
| `std::exception` | 标准异常的通用基类，适合最后一级统一记录或终止。 |

`std::exception::what()` 返回一个以空字符结尾的说明字符串。它用于诊断和日志，不应把程序逻辑建立在某个实现的具体文字上；需要判断错误类别时，应按异常类型捕获，或在自定义异常中提供明确的错误码。

当标准异常类型不能充分表达领域语义时，可以从 `std::runtime_error` 或 `std::logic_error` 派生自定义异常：

~~~cpp
#include <stdexcept>
#include <string>

class ConfigError : public std::runtime_error {
public:
    explicit ConfigError(const std::string& message)
        : std::runtime_error(message) {}
};
~~~

自定义异常应尽量包含有助于处理的上下文，但不要把敏感信息（密码、访问令牌、个人数据）直接写进异常消息。若需要让上层区分机器可读的错误类型，可以增加枚举值或错误码；不要要求上层解析中文错误消息。

### 6. 在哪里抛出、在哪里捕获

一个实用原则是：

- **在最早能发现错误的地方抛出**，这样错误上下文最准确。
- **在最有能力恢复的地方捕获**，例如输入层可以重新提示，服务层可以切换备用方案，程序最外层可以记录日志并安全退出。
- 如果当前层无法恢复，不要捕获后静默忽略；可以让异常继续传播，或补充上下文后重新抛出。

下面几种写法不要混淆：

~~~cpp
try {
    do_work();
} catch (const std::exception& error) {
    log(error.what());
    throw;       // 重新抛出当前异常对象，保留原来的动态类型
}

try {
    do_work();
} catch (const std::exception& error) {
    log(error.what());
    throw std::runtime_error("更上层看到的统一错误");
    // 抛出一个新异常；原异常不会自动保留
}
~~~

`throw;` 只能在正在处理异常的 `catch` 中用于重新抛出当前异常。在 `catch` 中写 `throw error;` 会把捕获变量当作一个普通表达式重新抛出，可能发生类型变化或切片，因此“记录并原样继续传播”时应写无操作数的 `throw;`。

捕获范围也不宜过大。把整个 `main` 或一大段不相关代码都包在一个 `try` 中，会让错误发生位置和恢复策略变得模糊；通常应在一个有明确事务边界的操作周围捕获。

### 7. 异常安全保证

**异常安全**描述的是：某个操作在异常发生时，是否仍能保持资源和对象状态的可靠性。常见的三种保证如下：

| 保证 | 含义 | 设计目标 |
| --- | --- | --- |
| 基本保证 | 不泄漏资源，类不变量仍成立，对象处于有效但状态可能改变的状态。 | 所有有副作用的操作至少做到这一点。 |
| 强保证 | 如果操作抛出异常，外部可观察状态保持不变，具有“要么全部成功、要么仿佛没发生”的效果。 | 适合配置更新、事务式修改等重要操作。 |
| 不抛保证 | 操作保证不会让异常逃出，例如析构、交换或明确标记为 `noexcept` 的函数。 | 清理和底层基础设施通常需要这一点。 |

“不抛保证”不是说函数内部绝对不能写 `throw`，而是不能让异常离开函数；如果异常从 `noexcept` 函数逃出，程序会调用 `std::terminate()`。异常安全保证也不是“捕获异常的技巧”，而是接口和资源所有权的整体设计。

实现强保证的常见办法是**先在临时对象中完成可能失败的工作，成功后再一次性提交**。例如：

~~~cpp
#include <utility>
#include <vector>

void append_strong(std::vector<int>& values, int value) {
    std::vector<int> copy = values; // 复制可能失败，但不会改动原对象
    copy.push_back(value);           // 扩容或构造元素可能失败
    values.swap(copy);               // 前面都成功后再提交修改
}
~~~

如果复制或 `push_back` 抛出异常，`values` 仍保持原来的内容；临时 `copy` 会在栈展开时自动销毁。`swap` 之后，原内容已经被安全地替换，旧内容由 `copy` 的析构负责释放。这种“准备—提交”结构通常比“先修改一半，再尝试回滚”更容易证明正确。

异常安全的基础是 RAII：资源必须由对象拥有，清理必须放在析构函数中。手写一串 `new`、`delete`、`close` 和多个 `catch`，很容易遗漏某条异常路径；应优先使用标准容器、智能指针、文件流和锁守卫。相关的对象销毁顺序见[[对象生命周期与RAII]]。

### 8. `noexcept`、析构函数与移动操作

`noexcept` 用来声明函数不会让异常逃出：

~~~cpp
void close_connection() noexcept {
    // 清理函数必须自行处理失败，不能把异常抛给析构调用者
}

void may_fail() noexcept(false) {
    // noexcept(false) 表示允许异常传播；这也是默认语义
}
~~~

`noexcept` 有两个常见误解：

1. 它不是“编译器保证函数永远不出错”，而是对调用者和编译器的契约。
2. 它不是 `try`/`catch`，也不会自动捕获异常。若异常离开 `noexcept` 函数，标准库会调用 `std::terminate()`，通常不会回到外层 `catch`。

析构函数通常应保持不抛异常，尤其是在栈展开期间。若一个异常正在传播，析构函数又抛出另一个异常，程序无法安全决定先处理哪一个，通常会直接调用 `std::terminate()`。关闭文件、释放锁、释放内存等清理动作应设计为不抛；如果“提交事务”或“刷新数据”可能失败，应提供显式的 `commit()`、`close()` 或 `flush()` 接口，让调用者在仍能处理错误的时机检查结果。

移动构造函数和移动赋值运算符也常标记为 `noexcept`。例如，标准容器在扩容搬移元素时，可能根据移动操作是否 `noexcept` 来决定使用移动还是复制，以维持异常安全。只有在移动确实不会抛出时才应写 `noexcept`，不要为了让代码“看起来现代”而做不真实的承诺。

如果一个函数需要条件式地声明不抛，可以使用 `noexcept(表达式)`：

~~~cpp
template <typename T>
void swap_values(T& a, T& b) noexcept(noexcept(std::swap(a, b))) {
    std::swap(a, b);
}
~~~

这类模板写法属于进阶内容。初学阶段只需记住：`noexcept` 应与真实行为一致，析构函数和资源清理路径尤其要谨慎。

### 9. Windows 环境中的编译和系统错误

本章示例只使用标准 C++，因此在 Windows 上不依赖 MFC、Win32 API 或第三方库。使用 Visual Studio 时，应在“Developer PowerShell for VS”中编译，并启用 C++ 异常语义：

~~~powershell
cl /std:c++17 /EHsc /W4 /permissive- exception_basic.cpp /Fe:exception_basic.exe
.\exception_basic.exe
~~~

`/EHsc` 告诉 MSVC 按标准 C++ 异常规则生成和处理代码；`/W4` 提高警告级别。使用已配置的 MinGW-w64 时：

~~~powershell
g++ -std=c++17 -Wall -Wextra -pedantic exception_basic.cpp -o exception_basic.exe
.\exception_basic.exe
~~~

Windows API 常使用返回值表示失败，并要求调用者通过 `GetLastError()` 查询错误码。不要直接把错误码当作通用 C++ 异常类型；在平台边界处可以转换为 `std::system_error`，让上层继续使用 C++ 异常体系：

~~~cpp
#include <system_error>
#include <windows.h>

void throw_last_windows_error(const char* operation) {
    const DWORD code = GetLastError();
    throw std::system_error(
        static_cast<int>(code), std::system_category(), operation);
}
~~~

只有在紧接着失败的 Windows API 调用之后读取 `GetLastError()` 才可靠；其他 API 调用可能改变它。并且 `GetLastError()` 的值只描述最近一次相关 Win32 调用的线程本地错误，不是全局错误变量。实际项目中还要按照具体 API 的文档判断失败值，例如有的 API 用 `nullptr` 表示失败，有的 API 使用 `INVALID_HANDLE_VALUE`。

### 10. 常见错误与排查清单

1. **捕获基类写在前面**：`catch (const std::exception&)` 会遮挡后面的派生类处理器。按“具体到一般”排序。
2. **按值捕获异常**：可能复制对象并造成切片。优先使用 `catch (const SomeError& error)`。
3. **只写 `catch (...)`**：看不到类型和消息，也容易误吞错误。把它作为最后的兜底，并记录、恢复或重新抛出。
4. **捕获后什么也不做**：空的 `catch` 会隐藏故障。至少要明确这是有意忽略，并确保对象状态和资源仍可靠。
5. **用 `throw error;` 原样重抛**：它不是严格意义上的原样重抛，可能改变类型。应使用无操作数的 `throw;`。
6. **抛出裸指针或字符串字面量**：调用者难以统一处理，指针还带来所有权和生命周期问题。优先抛出标准异常或自定义异常对象。
7. **以为 `try` 能修复未定义行为**：数组越界、释放后使用、数据竞争等问题发生后不能靠捕获异常恢复。
8. **手动资源管理没有覆盖异常路径**：`new` 后在下一行抛异常会泄漏。改用 `std::make_unique`、容器或其他 RAII 包装器。
9. **在析构函数中抛异常**：可能与已有异常叠加并导致 `std::terminate()`。把可报告的清理操作改成显式成员函数。
10. **随意标记 `noexcept`**：真实异常逃出后程序会终止，外层 `catch` 也接不到。只有确定不抛或内部完整处理时才使用。
11. **认为异常能跨线程传播**：不能直接跨线程；在线程函数内部捕获，或通过 `future` 等结果通道传递。
12. **使用已经过时的动态异常规格**：`throw(int)` 等动态异常规格在 C++17 中已移除，不要与 `noexcept` 混用。
13. **捕获范围过大**：整个程序只有一个模糊的 `catch`，往往无法恢复。围绕有明确职责和边界的操作捕获。
14. **用异常代替正常分支**：循环中把每个预期失败都变成异常，会让控制流难读。输入校验、查找失败等情况可考虑返回状态或 `std::optional`。

排查异常问题时可以按这个顺序思考：哪里抛出？抛出的动态类型是什么？哪一个 `catch` 首先匹配？传播时哪些对象会析构？资源是否由 RAII 类型拥有？当前层真的能恢复吗？如果没有匹配处理器，程序是否会在合适的最外层安全终止？

## 示例与实践

### 1. 完整可运行示例：捕获参数错误

将下面内容保存为 `exception_basic.cpp`。程序展示正常返回、抛出异常、按类型捕获，以及处理器结束后继续执行。它只需要 C++17 标准库：

~~~cpp
#include <iostream>
#include <stdexcept>

double divide(double dividend, double divisor) {
    if (divisor == 0.0) {
        // invalid_argument 说明调用者提供的参数不合法
        throw std::invalid_argument("除数不能为零");
    }
    return dividend / divisor;
}

int main() {
    try {
        const double valid_result = divide(10.0, 2.0);
        std::cout << "10 / 2 = " << valid_result << '\n';

        // 先调用再输出，避免异常发生时只输出半行提示
        const double invalid_result = divide(10.0, 0.0);
        std::cout << "10 / 0 = " << invalid_result << '\n';
        std::cout << "这一行不会输出\n";
    } catch (const std::invalid_argument& error) {
        std::cerr << "计算失败：" << error.what() << '\n';
    }

    std::cout << "异常已处理，程序继续运行。\n";
}
~~~

在 Visual Studio Developer PowerShell 中：

~~~powershell
cl /std:c++17 /EHsc /W4 /permissive- exception_basic.cpp /Fe:exception_basic.exe
.\exception_basic.exe
~~~

预期可以看到 `10 / 2` 的结果、错误信息以及最后的“程序继续运行”。第二次调用抛出异常后，`divide` 的 `return` 没有执行，`try` 中后续的输出也没有执行。

### 2. 完整可运行示例：解析输入并转换异常类型

下面的程序模拟读取配置文件中的端口号。`std::stoi` 负责底层字符串转换；`parse_port` 捕获底层异常并转换成更符合业务语义的 `ConfigError`，调用者只需要处理配置错误。示例使用固定输入以便每次运行结果稳定：

~~~cpp
#include <array>
#include <iostream>
#include <stdexcept>
#include <string>

class ConfigError : public std::runtime_error {
public:
    explicit ConfigError(const std::string& message)
        : std::runtime_error(message) {}
};

int parse_port(const std::string& text) {
    std::size_t parsed = 0;
    int port = 0;

    try {
        port = std::stoi(text, &parsed);
    } catch (const std::invalid_argument&) {
        // 不把底层库的英文消息直接暴露给配置层调用者
        throw ConfigError("端口必须是整数：" + text);
    } catch (const std::out_of_range&) {
        throw ConfigError("端口数值超出 int 范围：" + text);
    }

    if (parsed != text.size()) {
        throw ConfigError("端口包含无效字符：" + text);
    }
    if (port < 1 || port > 65535) {
        throw ConfigError("端口必须位于 1 到 65535 之间：" + text);
    }
    return port;
}

int main() {
    const std::array<std::string, 4> samples{
        "8080", "abc", "70000", "80http"
    };

    for (const std::string& text : samples) {
        try {
            const int port = parse_port(text);
            // 先完成解析，成功后再输出完整的一行
            std::cout << text << " -> " << port << '\n';
        } catch (const ConfigError& error) {
            // 这里是配置层，最适合给出提示或终止启动
            std::cout << text << " -> 配置错误："
                      << error.what() << '\n';
        }
    }
}
~~~

编译命令与上一个示例相同，只需把源文件名替换为 `config_demo.cpp`。这个例子还说明了“在哪里捕获”的原则：底层转换函数知道 `stoi` 的异常类型，配置层知道如何向用户解释；如果再上一层能够修复配置，还可以继续把错误传递给更上层。

### 3. 完整可运行示例：观察栈展开和 RAII 清理

将下面内容保存为 `exception_raii.cpp`。程序在写文件后故意抛出异常，用来观察：异常离开函数时局部对象仍会析构，`std::ofstream` 也会自动关闭文件。文件会创建在程序的当前工作目录中：

~~~cpp
#include <fstream>
#include <iostream>
#include <stdexcept>

class ScopeLog {
public:
    explicit ScopeLog(const char* name) : name_(name) {
        std::cout << name_ << " 构造\n";
    }

    ~ScopeLog() noexcept {
        std::cout << name_ << " 析构\n";
    }

private:
    const char* name_;
};

void write_then_fail() {
    ScopeLog scope("ScopeLog");
    std::ofstream file("exception_raii_output.txt");
    if (!file) {
        throw std::runtime_error("无法打开输出文件");
    }

    file << "这行内容已经写入文件。\n";
    if (!file) {
        throw std::runtime_error("写入文件失败");
    }

    throw std::runtime_error("模拟业务错误");
    // 异常发生后不会执行到函数末尾，但 file 和 scope 仍会清理
}

int main() {
    try {
        write_then_fail();
    } catch (const std::exception& error) {
        std::cout << "捕获到：" << error.what() << '\n';
    }

    std::cout << "main 正常结束。\n";
}
~~~

如果文件成功打开，输出中会先看到 `ScopeLog 析构`，然后看到捕获信息。`std::ofstream` 的析构函数负责关闭文件；不需要在每个 `throw`、`return` 和 `catch` 分支中重复写 `file.close()`。但要注意，RAII 负责资源清理，不会自动把写入失败变成异常，所以示例显式检查了流状态。

### 4. 完整可运行示例：用临时对象提供强异常安全保证

将下面内容保存为 `exception_safety.cpp`。`append_strong` 先复制并修改临时 `vector`，最后才交换到原对象；如果准备阶段出现异常，调用者看到的原对象不变：

~~~cpp
#include <iostream>
#include <stdexcept>
#include <vector>

void append_strong(std::vector<int>& values, int value) {
    if (value < 0) {
        // 这是可预期的参数错误，直接拒绝，不修改原 vector
        throw std::invalid_argument("只允许添加非负数");
    }

    std::vector<int> copy = values; // 可能分配内存，但原对象还未修改
    copy.push_back(value);           // 可能扩容；失败时 copy 会自动清理
    values.swap(copy);               // 准备成功后一次性提交
}

void print_values(const std::vector<int>& values) {
    for (int value : values) {
        std::cout << value << ' ';
    }
    std::cout << '\n';
}

int main() {
    std::vector<int> values{1, 2, 3};
    std::cout << "初始内容：";
    print_values(values);

    try {
        append_strong(values, -1);
    } catch (const std::invalid_argument& error) {
        std::cout << "操作失败：" << error.what() << '\n';
    }

    std::cout << "失败后的内容：";
    print_values(values); // 仍然是 1 2 3

    append_strong(values, 4);
    std::cout << "成功后的内容：";
    print_values(values); // 变成 1 2 3 4
}
~~~

这个例子不是说复制永远是最高效的方案，而是用简单结构展示“准备—提交”的思路。在性能敏感的代码中，应结合具体数据结构、事务接口和标准库保证选择实现方式；首先要保证对象状态和资源管理正确，再做优化。
