# 互斥、锁与条件变量

## 学习目标

- [ ] 理解共享状态、临界区、数据竞争和未定义行为的关系。
- [ ] 使用 `std::mutex`、`std::lock_guard` 和 `std::unique_lock` 安全地保护共享数据。
- [ ] 使用 `std::condition_variable` 实现“没有工作就等待，有工作再唤醒”。
- [ ] 能解释伪唤醒、丢失唤醒、死锁和锁粒度过大等问题。

## 先建立一个直觉：线程之间共享的是“状态”

多个线程如果只操作各自的局部变量，通常不需要额外同步；真正困难的是它们访问同一份可变数据。例如，`counter++` 看起来是一条语句，实际上至少包含“读、加一、写回”三个步骤：

```cpp
// 错误示例：两个线程同时执行 counter++。
int counter = 0;

// 线程 A 和线程 B 都可能先读到 0，再分别写回 1。
// 最后 counter 可能是 1，而不是预期的 2。
++counter;
```

如果一个线程正在写，另一个线程同时读或写普通的 `int`，就可能产生 **数据竞争（data race）**。在 C++ 中，数据竞争会导致未定义行为。互斥锁的作用，就是让相关操作形成一个不可同时进入的 **临界区（critical section）**。

可以把互斥锁想象成一把房间钥匙：同一时刻只有拿到钥匙的线程可以进入；离开时必须归还。这个比喻有一个前提：**所有访问这间“房间”的代码都必须使用同一把钥匙**。只在某些地方加锁，不能保护数据。

## 一、`std::mutex` 与 RAII 锁

`std::mutex` 位于 `<mutex>` 头文件中，提供最基础的 `lock()` 和 `unlock()`。通常不要直接手写它们，因为中间一旦 `return`、抛出异常或新增提前退出路径，就可能忘记解锁。更安全的做法是使用 RAII 锁守卫，让对象构造时加锁、析构时自动解锁。

### 1. 用 `std::lock_guard` 保护临界区

```cpp
#include <iostream>
#include <mutex>
#include <thread>
#include <vector>

int counter = 0;
std::mutex counter_mutex;

void add_many_times()
{
    for (int i = 0; i < 100'000; ++i) {
        // 构造 lock_guard 时加锁。
        std::lock_guard<std::mutex> lock(counter_mutex);
        ++counter; // 只有持锁线程能修改 counter
        // 本轮结束时 lock 析构，自动解锁。
    }
}

int main()
{
    std::vector<std::thread> workers;
    for (int i = 0; i < 4; ++i) {
        workers.emplace_back(add_many_times);
    }
    for (auto& worker : workers) {
        worker.join(); // 先等待线程结束，再销毁共享对象
    }
    std::cout << counter << '\n'; // 预期输出 400000
}
```

临界区应尽量小，只包含维持共享状态一致性所必需的代码。文件 I/O、网络请求和长时间计算通常应放在锁外，否则其他线程会无意义地排队。

### 2. 常用锁管理器

| 类型 | 特点 | 适合场景 |
| --- | --- | --- |
| `std::lock_guard` | 立即加锁，析构时解锁；不能提前解锁 | 简单、短小的临界区 |
| `std::unique_lock` | 可延迟加锁、提前解锁、重新加锁 | 条件变量或分段持锁 |
| `std::scoped_lock` | 一次安全锁住一个或多个互斥量 | 同时锁多把锁 |

不要写成下面这样：

```cpp
std::lock_guard<std::mutex>(counter_mutex); // 临时对象立即析构
++counter;                                  // 下一行已经没有锁
```

应当给锁守卫起变量名：

```cpp
std::lock_guard<std::mutex> lock(counter_mutex);
++counter;
```

`std::condition_variable::wait` 要求 `std::unique_lock`，因为等待时需要暂时解锁，被唤醒后再重新加锁；`lock_guard` 没有这种能力。

## 二、把锁和数据放在一起

如果一个类的成员必须一起保持一致，就让类自己持有互斥量，并在成员函数内部统一保护：

```cpp
#include <mutex>

class BankAccount {
public:
    void deposit(int amount)
    {
        std::lock_guard<std::mutex> lock(mutex_);
        balance_ += amount;
    }

    bool withdraw(int amount)
    {
        std::lock_guard<std::mutex> lock(mutex_);
        if (amount > balance_) {
            return false; // 检查与修改必须在同一个临界区
        }
        balance_ -= amount;
        return true;
    }

    int balance() const
    {
        std::lock_guard<std::mutex> lock(mutex_);
        return balance_; // 返回副本，不暴露内部引用
    }

private:
    mutable std::mutex mutex_; // const 成员函数也需要加锁
    int balance_ = 0;
};
```

加锁后不要把内部数据的引用或指针交给调用者，再在解锁后使用它。锁只保护持锁期间的访问，不能延长数据的安全生命周期。

## 三、多把锁与死锁

**死锁（deadlock）** 是线程互相等待，谁也无法继续：

```cpp
// 线程 A：先拿 mutex_a，再等待 mutex_b
// 线程 B：先拿 mutex_b，再等待 mutex_a
// 两个线程会永久等待对方释放第二把锁。
```

规约一是所有代码都按同一个顺序加锁；规约二是使用 `std::scoped_lock` 一次性获取多把锁：

```cpp
#include <mutex>

void operate_on_two_objects(std::mutex& first_mutex,
                            std::mutex& second_mutex)
{
    // 标准库会采用避免死锁的锁定算法。
    std::scoped_lock locks(first_mutex, second_mutex);
    // ...同时访问两个对象...
}
```

如果只想尝试加锁而不愿等待，可以使用 `try_lock()` 或 `std::try_to_lock`，但失败后的业务处理必须明确，不能悄悄跳过保护。

## 四、条件变量：等待状态变为可用

互斥锁只能回答“现在谁可以访问共享状态”，不能回答“什么时候有工作可做”。消费者发现队列为空时，如果反复检查会浪费 CPU，这叫忙等。`std::condition_variable` 允许线程在条件不满足时睡眠，让出 CPU；生产者改变状态后通知它醒来。

它通常和三样东西一起出现：

1. 保存真实状态的共享变量，例如队列、`closed` 标志或任务数量。
2. 一把保护该状态的互斥锁。
3. 一个条件变量，用于等待和通知。

### `wait` 的正确模型

```cpp
std::unique_lock<std::mutex> lock(mutex);
condition.wait(lock, [] {
    return condition_is_true();
});
```

带谓词的 `wait` 可以理解为：

```cpp
while (!condition_is_true()) {
    // wait 会暂时释放 lock 并睡眠；被唤醒后重新拿回 lock
    condition.wait(lock);
}
```

谓词是对共享状态的判断，不是“通知是否到达”。条件变量本身不保存通知，通知只是提醒线程“可以重新检查状态了”。因此即使通知发生在线程开始等待之前，只要共享状态已经满足条件，线程也不会错误地睡眠。

### 为什么必须防范伪唤醒

线程可能在没有有效通知时从 `wait` 返回，这叫 **伪唤醒（spurious wakeup）**。多个消费者也可能同时被唤醒，但只有一个抢到最后一项工作，所以不能醒来后直接取数据：

```cpp
condition.wait(lock);
auto value = queue.front(); // 错误：醒来时队列仍可能为空
```

必须使用谓词版本，或手写 `while` 循环重新检查状态。`if` 不够，`while` 才正确。

## 五、完整示例：有界生产者—消费者队列

队列满时生产者等待，队列空时消费者等待；调用 `close()` 后，所有等待线程都会被唤醒并安全退出。

```cpp
#include <condition_variable>
#include <cstddef>
#include <deque>
#include <iostream>
#include <mutex>
#include <optional>
#include <stdexcept>
#include <thread>

class BoundedQueue {
public:
    explicit BoundedQueue(std::size_t capacity) : capacity_(capacity)
    {
        if (capacity_ == 0) {
            throw std::invalid_argument("capacity must be greater than zero");
        }
    }

    bool push(int value)
    {
        std::unique_lock<std::mutex> lock(mutex_);
        // wait 会暂时解锁，让消费者取数据；醒来后重新加锁并检查谓词。
        not_full_.wait(lock, [this] {
            return queue_.size() < capacity_ || closed_;
        });

        if (closed_) {
            return false; // close() 后不再接受新数据
        }
        queue_.push_back(value); // 持有 mutex_ 时修改队列

        lock.unlock();
        not_empty_.notify_one();
        return true;
    }

    std::optional<int> pop()
    {
        std::unique_lock<std::mutex> lock(mutex_);
        not_empty_.wait(lock, [this] {
            return !queue_.empty() || closed_;
        });

        // 关闭后可能还有剩余数据；只有“关闭且为空”才真正结束。
        if (queue_.empty()) {
            return std::nullopt;
        }
        int value = queue_.front();
        queue_.pop_front();

        lock.unlock();
        not_full_.notify_one();
        return value;
    }

    void close()
    {
        {
            std::lock_guard<std::mutex> lock(mutex_);
            closed_ = true; // 先改变谓词依赖的状态
        }
        // 关闭可能影响多个等待线程，所以使用 notify_all。
        not_full_.notify_all();
        not_empty_.notify_all();
    }

private:
    std::mutex mutex_;
    std::condition_variable not_empty_;
    std::condition_variable not_full_;
    std::deque<int> queue_;
    const std::size_t capacity_;
    bool closed_ = false;
};

int main()
{
    BoundedQueue queue(2);

    std::thread producer([&] {
        for (int i = 1; i <= 5; ++i) {
            if (!queue.push(i)) {
                return;
            }
        }
        queue.close();
    });

    std::thread consumer([&] {
        while (auto value = queue.pop()) {
            std::cout << "consume " << *value << '\n';
        }
        std::cout << "queue closed\n";
    });

    producer.join();
    consumer.join();
}
```

编译命令（C++17）：

```text
GCC / Clang: g++ -std=c++17 -pthread queue.cpp -o queue
MSVC: cl /std:c++17 /EHsc queue.cpp
```

关键点：`push` 等待“有空位或已关闭”；`pop` 等待“有数据或已关闭”。`close()` 必须先改变状态，再 `notify_all()`，否则睡眠中的线程可能永远不会醒来。通知不代替加锁，修改队列和关闭标志时仍必须持有互斥锁。

## 六、超时等待

不能无限等待时，可以使用 `wait_for` 或 `wait_until`。带谓词的重载会在超时后返回 `false`，也能防范伪唤醒：

```cpp
#include <chrono>

std::unique_lock<std::mutex> lock(mutex);
bool ready = condition.wait_for(
    lock,
    std::chrono::seconds(1),
    [&] { return !queue.empty() || closed; });

if (!ready) {
    // 一秒内条件仍未满足：可以重试、记录日志或返回超时错误。
}
```

## 七、常见错误清单

1. 只给写操作加锁：只要读写可能并发，读操作也需要同步。
2. 以为“通知会被记住”：条件变量不是事件队列，状态才是事实，通知只是提示。
3. 用 `if` 代替 `while`：使用 `wait(lock, predicate)` 最不容易写错。
4. 持锁执行慢操作：网络请求、文件 I/O、用户回调和长时间计算通常应移到锁外。
5. 锁的生命周期比线程短：线程仍在访问互斥量时，拥有它的对象不能析构；通常先 `join()` 再销毁共享对象。

## 八、如何选择同步工具

1. 多线程要修改一组相关数据，或需要“检查后再修改”时，优先使用互斥锁。
2. 线程需要等待队列、任务数量或关闭状态时，使用条件变量 + 互斥锁 + 谓词。
3. 只有一个简单独立状态，且操作可以用原子读改写表达时，才考虑 `std::atomic`；原子变量不能替代保护复杂对象。
4. 多线程主要读取、偶尔写入时，可以进一步了解 `std::shared_mutex`，但先掌握普通 `std::mutex`。

### 练习

- 把计数器改成一个类，隐藏 `counter` 和 `mutex`，再增加 `reset()`。
- 为 `BoundedQueue` 增加 `try_push()`：队列满时立即返回，不等待。
- 故意删除 `pop()` 的谓词，说明为什么伪唤醒或多消费者竞争会造成问题。

## 速记

```text
共享可变状态  ->  明确不变量  ->  用同一把 mutex 保护
需要等待状态  ->  unique_lock + condition_variable + while/谓词
多把锁        ->  统一顺序或 scoped_lock
退出程序      ->  先改变关闭状态，再 notify_all，最后 join 线程
```
