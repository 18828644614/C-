# 性能分析与优化

## 学习目标

- [ ] 理解“先测量、再优化”的原因，能用基准测试得到可信的时间数据。
- [ ] 能用时间复杂度、内存访问和分配次数解释程序为什么慢。
- [ ] 会使用基本的分析工具定位热点，而不是凭感觉修改代码。
- [ ] 能选择合适的容器、算法和字符串处理方式，减少不必要的复制和分配。
- [ ] 能评估并发、编译器优化和 I/O 优化的实际收益，并识别常见误区。

## 一、性能优化到底在优化什么

“性能”不是一个单独的数字。通常至少要区分以下指标：

| 指标 | 含义 | 例子 |
| --- | --- | --- |
| 延迟（latency） | 一次操作完成需要多久 | 一个请求从收到到返回用了 20 ms |
| 吞吐量（throughput） | 单位时间完成多少工作 | 每秒处理 10 000 条记录 |
| CPU 使用率 | CPU 忙碌的比例 | 程序只占一个核心的 80% |
| 内存占用 | 程序使用了多少内存 | 峰值占用 200 MB |
| 尾延迟（tail latency） | 最慢的一小部分请求需要多久 | P99 延迟为 150 ms |

初学时最重要的原则是：**先明确要改善哪个指标，再开始测量**。降低平均耗时，却让 P99 变差，不能算作全面的优化；把 CPU 用满，也不一定代表吞吐量更高。

性能优化还必须保持程序的正确性。一个更快但结果错误的程序没有价值。建议把优化过程固定成下面的闭环：

~~~text
提出可验证的假设 → 建立基线 → 测量/分析 → 修改一个因素
        ↑                                      ↓
        └──────────── 正确性测试 + 复测 ←───────┘
~~~

不要一开始就“把所有地方都改一遍”。一次只改一个主要因素，才能知道收益来自哪里，也更容易在收益不明显时撤销修改。

## 二、先建立可靠的基准测试

### 2.1 `steady_clock`：测量经过的时间

墙上时钟可能因为系统校时而跳动；测量耗时时应优先使用单调递增的 `std::chrono::steady_clock`：

~~~cpp
#include <chrono>
#include <iostream>

int main() {
    using clock = std::chrono::steady_clock;

    const auto begin = clock::now();

    // 被测代码放在计时区间内。
    for (volatile int i = 0; i < 1'000'000; ++i) {
        // volatile 只在这个教学示例中防止循环被完全删除；
        // 它不是线程同步工具，也不是正式基准测试的万能方案。
    }

    const auto end = clock::now();
    const auto elapsed = std::chrono::duration_cast<std::chrono::microseconds>(
        end - begin);
    std::cout << "耗时：" << elapsed.count() << " us\n";
}
~~~

`duration_cast` 只是改变显示单位，并不会让测量更精确。短到几纳秒的代码，计时器调用本身可能比被测代码还“贵”，应当把操作重复很多次，再计算每次平均耗时。

### 2.2 一个适合入门的微型基准

~~~cpp
#include <algorithm>
#include <chrono>
#include <cstddef>
#include <iostream>
#include <string>
#include <vector>

std::size_t count_digits(const std::string& text) {
    return static_cast<std::size_t>(std::count_if(
        text.begin(), text.end(), [](unsigned char ch) {
            return ch >= '0' && ch <= '9';
        }));
}

int main() {
    const std::string input(100'000, '7');
    constexpr int warmups = 3;
    constexpr int rounds = 10;
    constexpr int repetitions = 100;
    std::vector<double> milliseconds;

    // 预热：第一次运行可能包含缓存建立、动态库加载等一次性成本。
    for (int i = 0; i < warmups; ++i) {
        const auto ignored = count_digits(input);
        (void)ignored;
    }

    for (int round = 0; round < rounds; ++round) {
        const auto begin = std::chrono::steady_clock::now();
        std::size_t result = 0;
        for (int i = 0; i < repetitions; ++i) {
            result += count_digits(input);
        }
        const auto end = std::chrono::steady_clock::now();

        // result 必须在计时区间外使用，否则优化器可能删除整个循环。
        std::cout << "本轮结果（防止代码被消除）：" << result << '\n';
        const std::chrono::duration<double, std::milli> elapsed = end - begin;
        milliseconds.push_back(elapsed.count() / repetitions);
    }

    // 中位数比单次结果更不容易受到系统后台任务的影响。
    std::sort(milliseconds.begin(), milliseconds.end());
    std::cout << "中位耗时：" << milliseconds[milliseconds.size() / 2]
              << " ms/次\n";
}
~~~

这个示例仍不是专业基准框架，适合用来理解方法。正式项目可使用 Google Benchmark 等框架，它会自动处理重复次数、统计和防止优化器消除结果等细节。

### 2.3 为什么“运行一次”通常不可信

一次运行会受到很多因素影响：

- CPU 频率会动态升降，笔记本还可能因为温度降频；
- 操作系统可能在后台调度其他进程；
- 第一次访问代码或数据时会发生缺页、缓存未命中和动态库加载；
- Debug 构建和 Release 构建的优化级别不同；
- 输入规模太小，计时器和函数调用的开销占了大部分。

基准测试应记录编译器、编译选项、操作系统、输入规模和硬件。优化前后的测试必须使用相同条件，并至少重复多轮；若结果波动很大，先找出波动来源，不要只挑一个“最好看的数字”。

## 三、复杂度：先解决增长速度，再纠结常数

### 3.1 大 O 表示输入变大时如何增长

常见复杂度可以先这样记：

| 复杂度 | 直觉 | 典型操作 |
| --- | --- | --- |
| `O(1)` | 与元素数量无关 | `vector[i]` 随机访问 |
| `O(log n)` | 每一步排除一半候选 | 有序数组二分查找 |
| `O(n)` | 每个元素看一次 | 遍历 `vector` |
| `O(n log n)` | 分治后合并 | `std::sort` 平均情形 |
| `O(n²)` | 元素两两比较 | 简单的双重循环 |

例如，在一百万条记录中为每条记录线性查找一次，最坏可能接近一万亿次比较；把查找表改成 `std::unordered_set` 或先排序后用二分，通常比“给循环加一点小技巧”有效得多。

~~~cpp
#include <algorithm>
#include <string>
#include <unordered_set>
#include <vector>

bool contains_slow(const std::vector<std::string>& names,
                  const std::vector<std::string>& queries) {
    for (const auto& query : queries) {
        // 每个 query 都扫描 names：O(names.size() * queries.size())。
        if (std::find(names.begin(), names.end(), query) != names.end()) {
            return true;
        }
    }
    return false;
}

bool contains_fast(const std::vector<std::string>& names,
                   const std::vector<std::string>& queries) {
    std::unordered_set<std::string> lookup(names.begin(), names.end());
    for (const auto& query : queries) {
        // 平均接近 O(1)，总成本约为建立集合 O(n) + 查询 O(m)。
        if (lookup.contains(query)) { // C++20
            return true;
        }
    }
    return false;
}
~~~

`unordered_set` 的“平均 `O(1)`”不是绝对保证：哈希冲突、糟糕的哈希函数和内存访问模式都会影响实际速度。复杂度用于选择方向，最终仍要用数据测量。

### 3.2 复杂度之外还有常数和输入分布

两个 `O(n)` 算法不一定一样快。一个只顺序读取连续的 `int`，另一个每次都追踪指针并造成缓存未命中，常数可能相差很多。输入是否已经有序、是否经常提前找到结果，也会改变平均耗时。

先用复杂度排除明显的数量级问题，再用基准和分析工具处理常数、缓存、分支和分配问题。

## 四、内存布局与 CPU 缓存：为什么连续数据往往更快

CPU 读取内存不是“一次取一个整数”，而是按缓存行（常见为 64 字节左右）把相邻数据一起带入缓存。顺序访问 `std::vector<int>` 时，下一项通常已经在缓存中；链表节点分散在堆上，遍历时可能每一步都等待内存。

~~~cpp
#include <list>
#include <vector>

long long sum_vector(const std::vector<int>& values) {
    long long sum = 0;
    for (int value : values) {
        sum += value; // 连续内存，访问模式对缓存友好。
    }
    return sum;
}

long long sum_list(const std::list<int>& values) {
    long long sum = 0;
    for (int value : values) {
        sum += value; // 节点可能散落在堆上，指针跳转更多。
    }
    return sum;
}
~~~

这并不表示 `vector` 永远优于 `list`。如果程序需要在中间位置频繁插入，并且已经持有稳定迭代器，链表可能更合适；但“只遍历一次”的场景通常应优先考虑连续容器。选容器时同时看操作需求、迭代器失效规则和内存占用。

数据结构还会影响“伪共享”（false sharing）：两个线程修改位于同一缓存行的不同变量时，缓存行会在核心之间反复转移，即使它们没有逻辑上的共享。遇到高并发热点时再用性能分析工具确认，不要一开始就手动填充结构体。

## 五、减少不必要的分配、复制和临时对象

### 5.1 `reserve`：提前告诉 `vector` 大小

`vector` 容量不足时会申请更大的内存，并移动或复制已有元素。反复扩容会浪费时间。若能估计元素数量，提前 `reserve`：

~~~cpp
#include <vector>

std::vector<int> make_values(int count) {
    std::vector<int> values;
    values.reserve(static_cast<std::size_t>(count));

    for (int i = 0; i < count; ++i) {
        values.push_back(i); // 容量足够时不会因扩容搬家。
    }
    return values; // 返回值通常会触发移动或返回值消除。
}
~~~

不要无条件写 `reserve` 一个极大的数字：它可能造成不必要的内存占用，甚至让分配失败。估计值不准时，适度预留即可。

### 5.2 `size`、`capacity` 和 `shrink_to_fit`

- `size()` 是当前元素数量；
- `capacity()` 是无需重新分配还能容纳多少元素；
- `reserve(n)` 至少保证容量为 `n`，不会改变 `size()`；
- `shrink_to_fit()` 只是非强制请求，不能保证一定释放内存。

~~~cpp
std::vector<int> values;
values.reserve(100); // size 仍然是 0
values.push_back(42); // size 变为 1
~~~

### 5.3 传参方式：先表达所有权，再考虑成本

常见经验如下：

~~~cpp
#include <string>

void inspect(const std::string& text); // 只读，不复制
void modify(std::string& text);        // 需要修改调用者对象
void take_ownership(std::string text); // 函数取得一份自己的值
~~~

`std::string` 很短时可能使用小字符串优化（SSO），不需要堆分配；很长时复制会复制字符并分配内存。因此不要背诵“引用总是更快”：若函数本来就要保存一份副本，按值传入再移动可能更清晰：

~~~cpp
#include <string>
#include <utility>

class User {
public:
    // 按值接收：左值调用会复制一次，右值调用可以移动；
    // 成员初始化再移动一次，避免为了两种情况写两个重载。
    explicit User(std::string name) : name_(std::move(name)) {}

private:
    std::string name_;
};

std::string source = "a long name";
User first(source);             // 需要复制 source
User second(std::move(source)); // 允许把 source 的缓冲区移动给对象
// 移动后的 source 仍然是有效字符串对象，但内容处于未指定状态；不要依赖原内容。
~~~

移动通常只是交换指针等少量信息，但不保证所有类型都便宜。只有在对象确实不再需要时才使用 `std::move`，它不会自动执行移动，也不会延长对象生命周期。

### 5.4 `std::string_view` 和 `std::span`：只借用，不拥有

只读函数不需要复制字符串或数组时，可以使用视图：

~~~cpp
#include <span>
#include <string_view>

bool has_error(std::string_view line) {
    return line.find("ERROR") != std::string_view::npos;
}

int sum(std::span<const int> values) {
    int result = 0;
    for (int value : values) {
        result += value;
    }
    return result;
}
~~~

视图只保存“指针 + 长度”，不拥有数据，因此必须保证被观察的对象活得更久：

~~~cpp
std::string_view bad_view() {
    std::string temporary = "hello";
    return temporary; // 错误：返回后 temporary 销毁，视图悬空。
}
~~~

不要从临时字符串、已释放的缓冲区或会扩容的 `vector` 上保存长期视图。视图适合在一个函数调用期间借用数据，不适合代替所有权。

## 六、算法和分支优化：先让代码表达正确意图

优先使用标准算法，编译器和库实现可能已经做过成熟优化：

~~~cpp
#include <algorithm>
#include <vector>

void remove_negative(std::vector<int>& values) {
    // erase-remove 惯用法：先把保留元素移到前面，再一次性删除尾部。
    const auto new_end = std::remove_if(values.begin(), values.end(),
                                        [](int value) { return value < 0; });
    values.erase(new_end, values.end());
}
~~~

分支预测也会影响实际速度。对随机数据，`if` 的结果难以预测；对长期保持同一结果的数据，CPU 更容易预测。不要为了消灭一个 `if` 就把代码改成难以维护的位运算，只有在分析工具显示该分支是热点时才考虑。

编译器通常能自动做循环展开、常量传播和内联。手写 `register`、随意添加 `inline`、把所有函数写成宏，并不能保证更快，反而可能损害可读性和调试能力。

## 七、I/O 优化：很多“计算慢”其实是在等待输入输出

终端输出非常慢。循环中逐条打印，往往比计算本身耗时几个数量级。先收集结果，再批量输出；需要大量标准输入时，可以关闭 C 和 C++ 流的自动同步：

~~~cpp
#include <iostream>

int main() {
    // 只有在程序不混用 scanf/printf 与 cin/cout 时才这样做。
    std::ios::sync_with_stdio(false);
    std::cin.tie(nullptr); // 不让每次 cin 前自动 flush cout

    long long value;
    long long sum = 0;
    while (std::cin >> value) {
        sum += value;
    }
    std::cout << sum << '\n'; // 最后只输出一次
}
~~~

`sync_with_stdio(false)` 不是“永远安全的加速开关”：调用后不要在同一程序中随意交替使用 `printf` 和 `std::cout`，否则输出顺序可能与预期不同。对于文件 I/O，还要考虑缓冲区大小、访问模式和磁盘本身的速度；不要把磁盘等待误判为 CPU 算法问题。

## 八、编译器优化与构建配置

Debug 版本常关闭优化并保留大量调试信息，便于断点；Release 版本通常开启优化，才接近用户实际运行速度。用 Debug 的耗时来判断 Release 程序，结论可能完全相反。

GCC/MinGW 的常见配置：

~~~powershell
# 调试：便于调试器观察变量
g++ -std=c++20 -Wall -Wextra -g -O0 main.cpp -o app-debug.exe

# 发布：常用的平衡优化级别
g++ -std=c++20 -Wall -Wextra -O2 main.cpp -o app-release.exe
~~~

MSVC 的对应思路是 Debug 使用较低优化并保留 `/Zi`，Release 常使用 `/O2`。具体选项应由项目的 CMake 配置统一管理，不要只在某个人的命令行里临时添加。

优化级别提高后，变量可能被消除或重排，断点处看到的值不一定与源代码逐行对应。若程序存在未定义行为，开启优化还可能暴露更多问题；应使用 [[调试与Sanitizer]] 检查越界、悬空指针和数据竞争，而不是“关闭优化来修复”它们。

## 九、用分析工具找到真正的热点

### 9.1 先用简单工具，再用采样分析器

按难度可以这样开始：

1. **计时器和基准测试**：比较一个明确的函数或操作。
2. **日志/计数器**：记录处理了多少数据、分配了多少次，以及其他可观察指标。
3. **采样 Profiler**：程序运行时定期记录当前调用栈，得到“时间花在哪里”。采样本身通常比给每行代码插桩更低干扰。
4. **硬件计数器**：进一步观察缓存未命中、分支预测失败和指令数，适合已经掌握基础后使用。

Windows 上可以使用 Visual Studio 的 Performance Profiler（CPU Usage、Instrumentation 等工具）；Linux 上常见 `perf`，也可以使用 Valgrind/Callgrind。不同平台的界面不同，但问题都是：找到最耗时的函数，再结合源码解释原因。

### 9.2 读懂热点报告

报告中的“某函数占 70% CPU”不一定表示它自己写得差：

- **Self time（自身时间）**：函数体本身消耗的时间；
- **Inclusive/Total time（包含时间）**：函数加上它调用的子函数的总时间；
- 如果 `main` 占 100%，这只表示所有工作都从 `main` 进入，不表示应该优化 `main`。

优化前先确认采样期间输入规模和场景具有代表性。一个只处理 10 个元素的微基准，不能证明真实服务在一百万元素时也更快。

## 十、并发优化：线程不是免费的

把任务拆成多个线程可能提高吞吐量，但会引入线程创建、任务调度、锁竞争、缓存一致性和结果合并成本。根据 Amdahl 定律，如果程序有一部分必须串行，并行加速存在上限：

~~~text
加速比 ≈ 1 / (串行比例 + 并行比例 / 线程数)
~~~

例如 10% 的工作无法并行，即使使用无限多个线程，理论加速比也不会超过 10 倍。实际还会更低，因为线程和同步本身有成本。

不要为每个小循环都创建线程：

~~~cpp
#include <future>
#include <numeric>
#include <vector>

int sum_in_parallel(const std::vector<int>& values) {
    const auto middle = values.size() / 2;

    // 任务足够大时，两个任务的计算时间才可能覆盖调度成本。
    auto left = std::async(std::launch::async, [&values, middle] {
        return std::accumulate(values.begin(), values.begin() + middle, 0);
    });
    auto right = std::async(std::launch::async, [&values, middle] {
        return std::accumulate(values.begin() + middle, values.end(), 0);
    });

    // 这里只读 values，因此两个任务之间没有写冲突。
    return left.get() + right.get();
}
~~~

上面的示例用于说明思路，并不保证比单线程 `std::accumulate` 快：数据太小、机器核心太少或任务创建成本较高时，可能更慢。应使用真实规模基准测试，并与单线程基线比较。锁竞争、忙等（不断轮询）和过多线程（oversubscription）是常见的并发性能问题，排查方法见 [[并发设计与同步策略]]。

## 十一、常见“优化”误区

1. **凭直觉优化**：没有基线就不知道是否变快，也不知道是否牺牲了别的指标。
2. **只测一次**：偶然的后台任务或 CPU 降频会改变结果。
3. **只看算法复杂度**：`O(n)` 仍可能因分配、缓存未命中或 I/O 而很慢。
4. **把 Debug 当 Release 测**：优化器可能完全改变代码路径。
5. **以为 `std::move` 到处都能加速**：移动后的对象内容不可依赖，某些类型移动也不便宜。
6. **把 `volatile` 当优化工具或同步工具**：它不能替代原子变量、锁，也不能保证代码更快。
7. **为了避免一次复制而引入悬空引用/视图**：生命周期正确性优先于微小收益。
8. **过早手写 SIMD、汇编或无锁结构**：先确认热点，再考虑复杂优化，并保留可测试的基线实现。
9. **只优化最容易改的地方**：应按 Profiler 的热点排序；优化一个只占 1% 时间的函数，整体最多只能快约 1%。

## 示例与实践

### 练习 1：比较 `reserve` 的影响

编写两个函数，分别向空 `vector` 插入一百万个整数，一个使用 `reserve`，另一个不使用。用多轮基准测试比较耗时，并记录 `size()` 与 `capacity()`。解释扩容时发生了什么。

### 练习 2：找出不必要的字符串复制

把一个接收 `std::string` 的只读函数改为 `std::string_view`，再测试以下情况：传入长字符串、短字符串和临时字符串。说明为什么临时字符串只能在调用期间安全地传给视图函数。

### 练习 3：算法复杂度

生成相同规模的名字列表和查询列表，比较双重线性查找与 `std::unordered_set` 查找。逐渐把输入扩大 10 倍，观察两种实现的耗时增长是否接近理论复杂度。

### 练习 4：建立优化报告

选择一个已有程序，写一页简短报告，至少包括：

- 优化目标（延迟、吞吐量或内存）；
- 测试环境、编译器和编译选项；
- 优化前基线、中位数和波动范围；
- Profiler 找到的热点和你的假设；
- 只改一个因素后的结果；
- 正确性测试结果，以及是否存在新的内存或并发风险。

完成本章后，应能回答：

- 为什么基准测试需要预热、重复和使用结果？
- 什么时候应该换算法或容器，什么时候才值得优化循环常数？
- `reserve`、移动语义、`string_view` 分别解决什么问题，又有什么生命周期风险？
- 如何区分 CPU 计算、内存访问、分配和 I/O 导致的慢？
- 为什么增加线程数不一定带来线性加速？
