# 并发设计与同步策略

## 学习目标

- [ ] 能把一个并发问题拆成“谁拥有数据、谁修改数据、线程如何通信”。
- [ ] 能区分共享状态、线程局部状态和只读状态。
- [ ] 能根据不变量和等待关系选择互斥锁、原子操作、条件变量或消息队列。
- [ ] 能设计线程的启动、停止、错误传播和资源回收流程。
- [ ] 能识别数据竞争、死锁、活锁、忙等和锁粒度过大等问题。

## 一、先建立正确的直觉：并发不是“多开几个线程”

并发设计真正要解决的问题是：**多个执行流如何安全地协作，同时尽量减少互相等待**。

可以把一个并发程序拆成三类东西：

| 问题 | 新手应该先问什么 | 常见答案 |
| --- | --- | --- |
| 数据 | 哪些数据会被多个线程看到？谁拥有它？ | 线程私有、只读共享、受保护的共享状态 |
| 通信 | 一个线程如何告诉另一个线程“有事可做”？ | 条件变量、队列、`future`、原子标志 |
| 生命周期 | 线程什么时候开始、停止和销毁？ | `join()`、`std::jthread`、协作式停止 |

很多并发 bug 并不是“锁写错了”，而是设计阶段没有回答这些问题。例如：一个线程把任务放进队列，另一个线程从队列取任务；如果没有规定谁负责关闭队列，消费者就可能永远等待，或者程序退出时仍在访问已经销毁的对象。

### 1. 线程安全不等于程序逻辑正确

线程安全通常只表示“没有数据竞争，访问不会破坏对象”。它不保证业务规则一定正确。

```cpp
// 两个操作各自加锁，但“检查余额”和“扣款”不是一个整体。
if (account.balance() >= 100) { // 读到余额
    account.withdraw(100);       // 之后再扣款
}
```

这里即使 `balance()` 和 `withdraw()` 内部各自使用了互斥锁，也不能保证“检查后扣款”这个业务动作不可被插入。更好的设计是提供一个原子化的业务操作：`try_withdraw(100)`，把检查和修改放在同一个临界区。

### 2. 优先减少共享，而不是先增加锁

并发设计通常有一个很实用的优先顺序：

1. 尽量让数据属于单个线程，避免共享。
2. 必须共享时，优先共享不可变数据。
3. 需要传递工作时，使用消息或任务队列，让线程交换“数据包”而不是直接改同一对象。
4. 最后才对确实需要共享的可变状态加锁或使用原子操作。

共享越少，需要推理的交互越少；交互越少，死锁和数据竞争越难出现。

## 二、四种常见的数据所有权模型

### 1. 线程局部数据：每个线程一份

如果每个线程只写自己的变量，就不需要为这个变量加锁。最后再由一个线程合并结果，这种方法通常比所有线程一起修改一个全局计数器更容易扩展。

```cpp
#include <cstddef>
#include <iostream>
#include <thread>
#include <vector>

int sum_part(const std::vector<int>& values,
             std::size_t begin,
             std::size_t end)
{
    int local_sum = 0; // 只属于当前线程，不需要加锁
    for (std::size_t i = begin; i < end; ++i) {
        local_sum += values[i];
    }
    return local_sum;
}

int main()
{
    const std::vector<int> values{1, 2, 3, 4, 5, 6};
    const auto middle = values.size() / 2;
    int left_sum = 0;
    int right_sum = 0;

    // 两个线程分别写不同的变量，因此没有同时写同一对象的数据竞争。
    std::thread left([&] {
        left_sum = sum_part(values, 0, middle);
    });
    std::thread right([&] {
        right_sum = sum_part(values, middle, values.size());
    });

    left.join();  // join 后，主线程才能安全读取 left_sum
    right.join(); // join 后，主线程才能安全读取 right_sum
    std::cout << left_sum + right_sum << '\n';
}
```

`values` 在两个线程中只读，因此可以安全共享；`left_sum` 和 `right_sum` 各自只有一个线程写。这里的 `join()` 不只是“等待”，还建立了线程结束前写入与主线程后续读取之间的同步关系。

### 2. 只读共享数据：构造后不再修改

只读数据可以被很多线程同时读取。例如配置表、查找表和已经构造完成的字符串。关键是要保证“发布”过程安全：对象必须先构造完，再交给其他线程使用；不能一边构造一边让其他线程读取。

```cpp
// 推荐：先在主线程中完整构造，再创建工作线程。
const std::vector<int> lookup_table = make_lookup_table();
std::thread worker([&lookup_table] {
    // 只读访问，不需要为每次查找加锁。
    use_table(lookup_table);
});
worker.join();
```

如果对象构造后仍会修改，就不再是只读共享数据，需要重新设计保护方式。

### 3. 受保护的共享状态：一把锁保护一个不变量

有些状态必须由多个线程共同维护，例如“余额不能为负”“队列大小不能超过容量”。这时要先写出不变量，再决定临界区边界。**同一个不变量涉及的检查和修改必须在同一个临界区内完成。**

```cpp
#include <mutex>

class Inventory {
public:
    bool try_buy(int count)
    {
        std::lock_guard<std::mutex> lock(mutex_);
        // 检查和扣减属于同一个业务动作，不能拆开。
        if (count < 0 || count > stock_) {
            return false;
        }
        stock_ -= count;
        return true;
    }

    int stock() const
    {
        std::lock_guard<std::mutex> lock(mutex_);
        return stock_; // 返回副本，不把内部引用带出锁的保护范围
    }

private:
    mutable std::mutex mutex_;
    int stock_ = 0;
};
```

这里使用一把锁保护 `stock_` 及其“不能减到负数”的规则。不要只给 `stock()` 加锁，却让 `try_buy()` 在锁外检查；那样检查到的值可能已经过期。

### 4. 消息传递：线程交换数据包

生产者和消费者不直接操作同一个业务对象，而是通过队列传递任务或结果。这样可以把共享区域缩小为“队列本身”，业务处理放在锁外执行。

```text
生产者线程 --push(任务)--> 线程安全队列 --pop(任务)--> 消费者线程
```

队列的完整实现见 [[互斥、锁与条件变量]] 的“有界生产者—消费者队列”示例。本章关注的是设计原则：队列需要明确容量、关闭方式、空队列等待方式，以及消费者在关闭后是否还要处理剩余任务。

## 三、先写不变量，再决定锁的范围

**不变量（invariant）** 是任何时刻都应该成立的规则。例如：

- `queue_.size() <= capacity_`；
- `balance_ >= 0`；
- `closed_ == true` 后，不再接受新任务；
- 一个任务最多只能被一个消费者取走。

一个常见错误是“每行代码都加锁”，却没有保护完整的不变量：

```cpp
// 错误思路：两个线程可能都通过检查。
if (stock.load() > 0) {
    stock.fetch_sub(1);
}
```

`load()` 和 `fetch_sub()` 虽然各自是原子的，但“检查后减一”不是一个原子业务动作。多个线程可能同时看到库存为 1，然后都尝试购买。可以使用 CAS 循环，或者对检查和修改整体加互斥锁。对于新手和复杂业务，互斥锁通常更容易证明正确。

### 临界区应该多大？

- 太小：不变量被拆散，容易在中间暴露不一致状态。
- 太大：线程持锁时间长，其他线程排队，吞吐量下降。

实用原则是：**临界区包含维护不变量所需的最少代码，但不包含可以独立进行的慢操作。**

```cpp
std::string message;
{
    std::lock_guard<std::mutex> lock(mutex_);
    message = make_message_from_state(); // 只在确实需要共享状态时持锁
}

// 网络请求、文件写入或用户回调放到锁外，避免长时间阻塞其他线程。
send_to_network(message);
```

如果 `send_to_network()` 必须使用锁内数据，应先复制出一个快照，再释放锁后发送。

## 四、同步工具的选择路径

可以按照下面的问题逐步判断：

### 问题 1：这个数据能不能不共享？

能：使用线程局部变量，任务结束后再合并结果。

不能：继续判断它是只读共享，还是可变共享。

### 问题 2：它是否只读？

是：在对象完整构造后发布给线程，通常不需要互斥锁。

否：继续判断修改是否只是一个独立值的简单读改写。

### 问题 3：是否只是一个独立计数、标志或指针？

是：可以考虑 `std::atomic`。例如统计请求次数、设置停止标志、抢占一个一次性任务。

```cpp
std::atomic<unsigned long> requests{0};
requests.fetch_add(1, std::memory_order_relaxed);
```

`relaxed` 只适合“这个数字本身就是全部含义”的情况。如果原子标志还要发布一批普通数据，需要使用 `release`/`acquire`，具体见 [[原子操作与内存模型]]。

### 问题 4：是否涉及多个字段、检查后修改或等待条件？

是：优先使用互斥锁；需要“没工作就睡眠，有工作再醒来”时，再加条件变量。

| 需求 | 首选工具 | 原因 |
| --- | --- | --- |
| 简单计数或停止标志 | `std::atomic` | 操作对象少，读改写可以表达为一个原子操作 |
| 多个字段必须一起更新 | `std::mutex` | 一把锁保护整体不变量 |
| 队列为空或已满时等待 | `mutex + condition_variable` | 等待时释放锁，不忙等 |
| 线程之间传递任务 | 线程安全队列或 `future` | 减少业务对象直接共享 |
| 多读少写的大型只读阶段 | `std::shared_mutex` | 允许多个读者，但使用前先确认读写比例 |

不要为了“看起来高级”而一开始就使用无锁算法、复杂内存序或共享锁。先写出容易验证的版本，再用基准测试确认瓶颈。

## 五、条件变量的设计：等待“状态”，不是等待“通知”

条件变量不保存通知。正确的模型是：

1. 用互斥锁保护真实状态，例如队列和 `closed` 标志。
2. 等待线程拿着 `unique_lock` 检查状态。
3. 状态不满足时调用 `wait`，它会暂时释放锁并睡眠。
4. 修改状态的线程先加锁修改状态，再通知等待者。

```cpp
std::unique_lock<std::mutex> lock(mutex_);
not_empty_.wait(lock, [this] {
    // 谓词判断真实状态，而不是判断“有没有收到通知”。
    return !queue_.empty() || closed_;
});

if (queue_.empty()) {
    return std::nullopt; // closed_ 且没有剩余数据：消费者结束
}

auto value = queue_.front();
queue_.pop_front();
```

必须使用谓词版本或 `while` 循环，因为存在伪唤醒；多个线程也可能同时醒来，但只有一个线程能取得最后一项任务。关闭时通常使用 `notify_all()`，让所有等待线程都有机会观察到 `closed_`。

## 六、锁的顺序：主动消灭死锁

死锁通常满足四个条件：互斥、占有并等待、不可剥夺、循环等待。设计时最容易控制的是“循环等待”：规定所有代码按同一个顺序获取锁。

```cpp
// 推荐：直接同时锁住多把锁，标准库会使用避免死锁的算法。
std::scoped_lock locks(first_mutex, second_mutex);
// 现在可以安全地访问两个对象。
```

如果无法同时锁住，至少规定全局顺序，例如所有代码先锁编号较小的对象，再锁编号较大的对象。还要避免在持锁期间调用未知代码，例如用户回调、插件代码或另一个可能再次加锁的成员函数。

## 七、线程生命周期：启动、停止、回收必须成对设计

并发对象通常按下面的顺序结束：

1. 阻止新任务进入，例如设置 `closed = true`。
2. 唤醒正在等待的线程，例如 `notify_all()`。
3. 让工作线程看到停止状态，并完成必要的收尾。
4. `join()` 等待线程结束。
5. 最后销毁队列、锁和线程访问的其他对象。

```cpp
#include <atomic>
#include <chrono>
#include <iostream>
#include <thread>

class Service {
public:
    void start()
    {
        worker_ = std::thread([this] {
            while (!stop_.load(std::memory_order_relaxed)) {
                do_one_piece_of_work();
                std::this_thread::sleep_for(std::chrono::milliseconds(10));
            }
        });
    }

    void stop()
    {
        stop_.store(true, std::memory_order_relaxed); // 先改变停止状态
        if (worker_.joinable()) {
            worker_.join(); // 确认线程不再访问 this 后，Service 才能析构
        }
    }

    ~Service()
    {
        stop(); // 析构时也要覆盖异常或提前返回路径
    }

private:
    void do_one_piece_of_work()
    {
        // 实际程序中不要访问已经由 stop() 销毁的资源。
        std::cout << "working\n";
    }

    std::atomic<bool> stop_{false};
    std::thread worker_;
};
```

`detach()` 会放弃管理线程的责任。除非已经设计好独立的资源生命周期和程序退出策略，否则新手应优先使用 `join()` 或 `std::jthread`。停止请求是协作式的，线程函数必须主动检查它，并不会被强制杀死。

## 八、完整设计示例：统计文件处理结果

假设要处理很多文件，并统计成功、失败数量。一个容易写错的版本是：所有线程都直接写全局 `success` 和 `failed`，然后为每次加一都竞争同一把锁。

更清晰的设计是：

- 文件列表只读共享；
- 每个线程拥有自己的局部统计；
- 最后由主线程合并统计；
- 错误信息通过结果队列或 `future` 传回。

```cpp
#include <cstddef>
#include <iostream>
#include <string>
#include <thread>
#include <vector>

struct Report {
    int success = 0;
    int failed = 0;
};

Report process_range(const std::vector<std::string>& files,
                     std::size_t begin,
                     std::size_t end)
{
    Report local; // 每个线程独有，循环内部不需要加锁

    for (std::size_t i = begin; i < end; ++i) {
        if (process_file(files[i])) {
            ++local.success;
        } else {
            ++local.failed;
        }
    }
    return local;
}

int main()
{
    const std::vector<std::string> files = load_file_list();
    const auto middle = files.size() / 2;
    Report left;
    Report right;

    std::thread a([&] {
        left = process_range(files, 0, middle);
    });
    std::thread b([&] {
        right = process_range(files, middle, files.size());
    });

    a.join();
    b.join();

    // 主线程在 join 后合并，避免让工作线程竞争同一个统计对象。
    const Report total{
        left.success + right.success,
        left.failed + right.failed,
    };
    std::cout << "success: " << total.success
              << ", failed: " << total.failed << '\n';
}
```

这个设计并不适合所有问题：如果任务数量动态变化，固定切成两段可能不均衡；这时可以使用任务队列和工作线程池。但核心思想保持不变：先确定所有权，尽量把共享缩小为只读输入和最终合并点。

## 九、常见错误与改进方向

### 1. “只给写操作加锁”

读线程如果可能与写线程并发，读操作同样需要同步。否则读线程可能看到中间状态，甚至触发数据竞争。

### 2. “有一个原子变量，所以整个对象都安全”

原子只保护它自己。一个原子版本号不能自动保护旁边的 `std::vector`；多个字段需要一起保持一致时，优先使用同一把互斥锁。

### 3. “通知一次就够了”

条件变量通知不保存事件。状态必须保存在队列、计数器或关闭标志中；等待者醒来后要重新检查状态。

### 4. “把锁范围扩大最安全”

锁范围过大虽然可能暂时掩盖设计问题，但会降低并发度，还可能在锁内调用慢操作或产生死锁。应先写不变量，再精确划分临界区。

### 5. “用 `sleep_for` 等待另一个线程”

睡眠只是在猜时间，不能保证状态已经改变。需要等待条件时，用 `condition_variable`；需要等待任务结果时，用 `future::get()`；需要等待线程结束时，用 `join()`。

### 6. “`detach()` 就是后台线程”

分离线程仍可能访问已经销毁的引用、对象或日志器。除非生命周期被明确设计，否则使用 `join()` 或 `std::jthread`。

### 7. 一开始就追求无锁

无锁算法需要精确理解 CAS、内存序、ABA 问题和对象生命周期。先用互斥锁写出可验证的版本，再通过性能测试判断是否真的需要优化。

## 十、设计检查清单

写并发代码前，可以逐项回答：

- [ ] 哪些对象被多个线程访问？哪些对象可以改成线程局部？
- [ ] 每个共享对象的所有者是谁？谁负责销毁它？
- [ ] 哪些字段组成同一个不变量？它们是否由同一把锁保护？
- [ ] 线程如何接收工作？队列为空时做什么？
- [ ] 队列或服务如何关闭？关闭后是否继续处理剩余任务？
- [ ] 谁负责 `join()`？如果中途抛出异常，线程是否仍会被回收？
- [ ] 是否在锁内执行了 I/O、网络请求、长计算或未知回调？
- [ ] 是否存在多个锁？所有路径是否按统一顺序获取？
- [ ] 原子操作是否只保护一个独立值？它是否错误地承担了发布复杂数据的职责？
- [ ] 是否用测试、ThreadSanitizer 或基准数据验证了设计，而不是只凭“看起来应该安全”？

## 练习

1. 把一个“所有线程共享一个全局计数器”的程序改成“每线程局部计数，最后合并”的版本，比较代码复杂度。
2. 为一个账户类增加 `try_transfer_to()`，保证扣款和入账要么一起完成，要么都不完成。
3. 为任务队列设计 `close()` 语义：关闭后是否允许消费者取出剩余任务？画出状态变化图。
4. 写两个会死锁的加锁顺序，再用 `std::scoped_lock` 或统一锁顺序修复。
5. 把 `sleep_for` 轮询停止标志的示例改成条件变量版本，使线程停止时可以立即被唤醒。

- 为什么“减少共享”通常比“增加锁”更容易得到正确程序？
- 一个不变量如何帮助我们确定临界区边界？
- 什么时候应该选择线程局部数据，什么时候应该选择任务队列？
- 为什么原子变量不能替代保护多个字段的互斥锁？
- 为什么关闭流程必须先改变状态、再通知、最后 `join()`？

## 速记

```text
先问所有权，再问同步
能不共享就不共享；能只读就只读
多个字段/检查后修改 -> mutex 保护一个完整不变量
独立计数/标志        -> atomic
需要等待状态          -> condition_variable + 谓词
线程传递工作          -> 线程安全队列或 future
退出                  -> 改变状态 -> 唤醒 -> join -> 销毁资源
多把锁                -> 统一顺序或 scoped_lock
```
