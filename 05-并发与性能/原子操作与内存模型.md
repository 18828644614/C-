# 原子操作与内存模型

## 学习目标

- [ ] 理解原子性、可见性、顺序和数据竞争之间的区别。
- [ ] 会用 `std::atomic` 实现简单计数器、标志和一次性状态转换。
- [ ] 能看懂 `load`、`store`、`fetch_add` 和 `compare_exchange` 的基本用法。
- [ ] 知道 `memory_order_relaxed`、`acquire`、`release` 和 `seq_cst` 分别解决什么问题。
- [ ] 能判断“一个原子变量”是否足以保护一组共享数据；不够时会改用互斥锁。

## 一、先建立直觉：并发难在哪里

当多个线程访问同一份可变数据时，问题不只是“谁先执行”。编译器和 CPU 为了提高性能，可能调整没有依赖关系的指令顺序；每个 CPU 核心还可能暂时使用自己的缓存。因此，另一个线程不一定立刻看到某次写入。

可以把并发安全拆成三个问题：

| 问题 | 要回答的事情 | 常见工具 |
| --- | --- | --- |
| 原子性（atomicity） | 一个操作会不会被拆成一半，让别人看到中间状态？ | `std::atomic`、互斥锁 |
| 可见性（visibility） | 一个线程的写入，何时对另一个线程可见？ | `release`/`acquire`、锁、`join()` |
| 顺序（ordering） | 多次读写在不同线程看来，先后关系是否有保证？ | 内存序、锁、线程同步 |

### 数据竞争就是未定义行为

如果两个线程并发访问同一个内存位置，至少一个访问是写入，而且访问之间没有同步，就产生 **数据竞争（data race）**。C++ 标准规定：数据竞争会导致未定义行为，不只是“结果偶尔不对”。

```cpp
int counter = 0;

// 错误：两个线程同时执行 ++counter。
// ++counter 实际上是“读 -> 加一 -> 写回”三个步骤。
// 两个线程可能都读到 0，最后都写回 1；更严重的是，这已经是数据竞争。
++counter;
```

**竞态条件（race condition）** 是更宽泛的说法：程序结果依赖线程时序。竞态条件有时是合法的（例如谁先完成都可以），而数据竞争一定是需要修复的未定义行为。

## 二、`std::atomic`：对一个值进行不可分割的操作

`std::atomic<T>` 位于 `<atomic>` 头文件中。它保证对这个原子对象的读、写和指定的读改写操作不会互相“撕裂”，并且这些操作之间遵守所选的内存序。

```cpp
#include <atomic>
#include <thread>
#include <vector>

std::atomic<int> counter{0};

void add_many_times() {
    for (int i = 0; i < 100'000; ++i) {
        ++counter; // 对 atomic<int> 来说，这是一个原子的读改写操作
    }
}

int main() {
    std::vector<std::thread> workers;
    for (int i = 0; i < 4; ++i) {
        workers.emplace_back(add_many_times);
    }
    for (auto& worker : workers) {
        worker.join(); // 等所有线程结束后再读取结果
    }
    // counter.load() 也可以写成 counter；这里显式写出“原子读取”。
    int result = counter.load();
}
```

上例中的四个线程最终会得到 `400000`。但要注意：`std::atomic<int>` 只保护 `counter` 这个对象。它不会自动保护旁边的普通变量、容器或“多个值之间的关系”。

### 2.1 常用操作

```cpp
std::atomic<int> value{10};

int a = value.load();          // 原子读取
value.store(20);               // 原子写入
int old = value.exchange(5);   // 写入 5，并返回旧值 20

int before = value.fetch_add(3); // 原子地加 3，返回加之前的值
int after = before + 3;

value.fetch_sub(1);            // 原子减法
value.fetch_or(0b0100);        // 对整数执行原子按位或（还有 and/xor）
```

`fetch_add` 很适合计数；`exchange` 很适合“只允许某个线程把状态从旧值替换成新值”的场景。原子操作返回旧值还是新值，要看函数的约定，使用前先查清楚。

### 2.2 用比较并交换（CAS）实现“如果仍然是旧值，就更新”

`compare_exchange`（通常简称 CAS）会比较原子变量当前值和 `expected`：

- 相等：写入 `desired`，返回 `true`；
- 不相等：不写入，返回 `false`，并把 `expected` 更新为当前值。

```cpp
#include <atomic>

std::atomic<int> maximum{0};

void update_max(int candidate) {
    int current = maximum.load(std::memory_order_relaxed);

    // 只在 candidate 更大时尝试更新最大值。
    while (current < candidate &&
           !maximum.compare_exchange_weak(
               current, candidate,
               std::memory_order_relaxed, // 成功时的内存序
               std::memory_order_relaxed  // 失败时的内存序
           )) {
        // CAS 失败时，current 已被改成“别人刚写入的值”，循环会重新判断。
    }
}
```

`compare_exchange_weak` 在某些平台上可能“无理由失败”（伪失败），所以通常放在循环里；`compare_exchange_strong` 不会伪失败，但在循环中未必更快。CAS 很强大，也更难读懂：如果只是保护一段复杂逻辑，优先使用 [[互斥、锁与条件变量]]。

### 2.3 原子类型的限制

整数、指针、`bool` 等类型最常见。`std::atomic<T>` 要求 `T` 满足相应的可复制/可赋值条件；不是所有复杂类型都能高效地原子操作。即使 `std::atomic<T>` 能编译，也不代表它一定是“无锁（lock-free）”的，库可能在内部使用锁：

```cpp
std::atomic<long long> number{0};
bool lock_free = number.is_lock_free(); // 运行时查询本平台实现
```

“无锁”是性能属性，不是正确性的前提。初学阶段先关注同步语义，不要为了追求无锁而牺牲可读性。

## 三、内存模型：编译器和 CPU 可以怎样重排

C++ 内存模型给每个线程一个 **线程内顺序**，并定义线程之间何时建立 **发生先于（happens-before）** 关系。只有建立了这种关系，我们才能从语言层面确定“某次写入一定先于某次读取，并且读取能看到它”。

下面的代码在单线程中显然按顺序执行：

```cpp
data = 42;
ready = true;
```

但在多线程中，另一个线程只看到 `ready == true`，并不自动意味着它能安全地读取 `data`。需要一个同步操作把两次访问连接起来。互斥锁的解锁/加锁、线程的 `join()`、原子的 `release`/`acquire` 都可以建立这种关系。

## 四、内存序从易到难

原子操作默认使用 `std::memory_order_seq_cst`（顺序一致性）。先用默认值写出正确程序，再在确实需要时考虑更弱的内存序。

### 4.1 `seq_cst`：最容易推理的默认选择

`seq_cst`（sequentially consistent）除了保证原子性，还尽量让所有线程看到一个一致的全局顺序。它通常最容易调试和解释，但可能限制编译器/CPU 的重排空间。

```cpp
std::atomic<bool> done{false};
done.store(true);       // 默认 seq_cst
if (done.load()) { /* ... */ }
```

对大多数业务代码和学习示例，默认内存序已经足够。不要把“更弱”误认为“更高级”。

### 4.2 `relaxed`：只要原子性，不建立通信关系

`memory_order_relaxed` 保证这个原子操作本身安全，但不保证它与其他普通读写的先后关系。它适合统计计数、采样次数等“数值本身不承担发布数据职责”的场景：

```cpp
std::atomic<unsigned long> requests{0};

void record_request() {
    // 只关心最终计数，不用这个计数来“发布”其他数据。
    requests.fetch_add(1, std::memory_order_relaxed);
}
```

重要反例：下面不能因为 `ready` 是原子变量就变安全。

```cpp
int data = 0;
std::atomic<bool> ready{false};

// 生产者
data = 42;
ready.store(true, std::memory_order_relaxed);

// 消费者
while (!ready.load(std::memory_order_relaxed)) {
    // 忙等
}
// data 的读写之间没有同步，仍然可能构成数据竞争。
int answer = data; // 不要这样写
```

### 4.3 `release` + `acquire`：发布数据，再安全读取

这是最值得掌握的模式：

1. 生产者先写普通数据；
2. 生产者对一个原子标志执行 `store(..., release)`，表示“之前的写入可以发布了”；
3. 消费者用 `load(..., acquire)` 读到这个标志为真；
4. 消费者随后读取普通数据。

```cpp
#include <atomic>
#include <iostream>
#include <thread>

int data = 0;                  // 只由生产者写，消费者在同步后读
std::atomic<bool> ready{false};

void producer() {
    data = 42; // 1. 先准备普通数据
    ready.store(true, std::memory_order_release);
    // 2. release 像一道“发布栅栏”：之前的 data=42 不能被挪到它后面
}

void consumer() {
    while (!ready.load(std::memory_order_acquire)) {
        // 3. acquire 读到 release 写入的 true 后，建立 happens-before
    }
    // 4. 此时 data=42 对当前线程可见，读取是安全的
    std::cout << data << '\n';
}

int main() {
    std::thread a(producer);
    std::thread b(consumer);
    a.join();
    b.join();
}
```

如果消费者的 `acquire` 读到了生产者 `release` 写入的值（或其释放序列中的值），生产者在 release 之前的写入就 **发生先于** 消费者 acquire 之后的读取。这里的关键不是“CPU 缓存立刻刷新”这种实现细节，而是 C++ 标准给出的可推理关系。

### 4.4 `acq_rel`：读改写操作同时需要获取和发布

`fetch_add`、`exchange`、成功的 CAS 等读改写操作可以使用 `memory_order_acq_rel`：它同时具有 acquire 和 release 的效果。只有在一个操作既要读取别人发布的状态，又要把自己的结果发布给后续线程时才需要它。失败的 CAS 不能使用 `release` 或 `acq_rel`，通常使用 `relaxed` 或 `acquire`。

### 4.5 `memory_order_consume` 与栅栏

`memory_order_consume` 的规则复杂，主流编译器通常按 `acquire` 处理；新手不要主动使用。`atomic_thread_fence`（内存栅栏）也属于进阶工具，只有在理解原子操作之间的同步关系、并有测量数据证明必要时再考虑。

## 五、原子变量不能替代互斥锁

### 5.1 一个值可以原子，不代表一组值一致

```cpp
#include <atomic>

struct Account {
    std::atomic<int> balance{0};
    std::atomic<int> version{0};
};

// 即使 balance 和 version 各自都是 atomic，
// 也不能保证读者同时看到“同一笔更新”的两个值。
```

如果不变量涉及多个字段（例如“余额和版本号必须同时改变”），用同一把互斥锁保护整个临界区通常更简单、更正确。

### 5.2 原子读改写不能自动完成业务流程

`if (stock > 0) --stock;` 包含检查和修改两个步骤。即使 `stock` 是原子变量，这两个操作分开写也可能被其他线程插入。应该使用 CAS 循环，或直接加锁：

```cpp
std::atomic<int> stock{10};

bool try_buy() {
    int old = stock.load(std::memory_order_relaxed);
    while (old > 0) {
        // 只有 old 仍是当前库存时才减一；否则 old 会被更新并重试。
        if (stock.compare_exchange_weak(
                old, old - 1,
                std::memory_order_relaxed,
                std::memory_order_relaxed)) {
            return true;
        }
    }
    return false; // 观察到库存为 0
}
```

这个例子只同步库存数字本身；如果购买还要修改订单、余额等其他状态，仍应使用互斥锁或更高层的事务设计。

## 六、C++20：原子等待与通知

忙等循环会持续占用 CPU。C++20 为原子变量提供了 `wait`/`notify_one`/`notify_all`，可以在值没有变化时阻塞，值改变后再唤醒：

```cpp
#include <atomic>
#include <iostream>
#include <thread>

std::atomic<int> state{0};

void worker() {
    // wait(0) 会等待 state 不再等于 0；实现可以在内部睡眠而非一直占用 CPU。
    state.wait(0, std::memory_order_acquire);
    std::cout << "开始工作\n";
}

int main() {
    std::thread t(worker);

    state.store(1, std::memory_order_release); // 先改变状态
    state.notify_one();                        // 再唤醒一个等待线程

    t.join();
}
```

`wait(old)` 的语义是“只要当前值仍等于 `old` 就等待”；它不是条件变量，真正的状态仍保存在原子变量中。需要同时等待队列、关闭标志等多个条件时，继续使用 [[互斥、锁与条件变量]] 更合适。

## 七、`volatile` 不是线程同步工具

`volatile` 主要用于内存映射硬件寄存器或与特殊信号处理交互，告诉编译器“每次都真的进行这次读写”。它不保证原子性，也不建立线程之间的 happens-before 关系：

```cpp
volatile bool ready = false; // 不能修复生产者/消费者的数据竞争
```

线程共享标志使用 `std::atomic<bool>`；共享复杂状态使用互斥锁。不要把 `volatile` 当作“防止编译器优化掉”的并发开关。

## 八、如何选择工具

1. 只共享一个独立计数、标志或指针，并且操作能表达为原子读改写：考虑 `std::atomic`。
2. 需要发布一批普通数据：用原子标志的 `release`/`acquire`，或使用互斥锁。
3. 需要同时维护多个字段、检查后再修改复杂状态、等待队列条件：优先使用互斥锁和条件变量。
4. 不确定内存序时：先使用默认 `seq_cst`，写测试和基准；确认正确性后再针对瓶颈局部改为 `relaxed` 或 `acquire`/`release`。
5. 需要线程结束后读取结果时：直接使用 `join()`；`join()` 本身就建立了必要的同步关系。

## 九、常见错误清单

1. 把 `counter++` 的原子版本和普通 `int` 混用：同一共享对象必须统一同步方式。
2. 只让“写入”原子化，却让关联的普通数据无同步地读取：原子标志需要配合 `release`/`acquire`。
3. 把 `relaxed` 当成“更快的万能内存序”：它只保证原子性，不负责发布数据。
4. 认为原子变量能保护 `std::vector`、字符串或多个字段：原子只覆盖它自己的那个对象。
5. 忽略 CAS 失败后 `expected` 会被更新：循环中要重新判断条件。
6. 用 `volatile` 替代 `std::atomic`：两者解决的问题不同。
7. 为了“无锁”手写复杂算法：先用锁写对，再用测量结果决定是否优化。
8. 让原子对象在线程仍使用时销毁：对象生命周期必须覆盖所有线程访问，通常先 `join()` 再销毁。

## 示例与实践

### 1. 可运行示例：安全的停止标志

```cpp
#include <atomic>
#include <chrono>
#include <iostream>
#include <thread>

std::atomic<bool> stop{false};

void worker() {
    while (!stop.load(std::memory_order_relaxed)) {
        // 做一小批工作；不要长时间不检查停止标志。
        std::this_thread::sleep_for(std::chrono::milliseconds(10));
    }
    std::cout << "worker stopped\n";
}

int main() {
    std::thread t(worker);
    std::this_thread::sleep_for(std::chrono::milliseconds(50));

    stop.store(true, std::memory_order_relaxed);
    t.join(); // join 保证 worker 已经观察到停止并结束
}
```

这里用 `relaxed` 是因为停止标志不负责发布其他数据；如果停止时还要让线程看到“收尾配置”，就应改用 `release`/`acquire`，并明确哪些写入需要被发布。

### 2. 编译命令（C++20 原子等待示例）

```text
GCC / Clang: g++ -std=c++20 -pthread atomic.cpp -o atomic
MSVC: cl /std:c++20 /EHsc atomic.cpp
```

## 练习

1. 把普通计数器改成 `std::atomic<int>`，分别尝试默认内存序和 `relaxed`，说明为什么结果都正确。
2. 修改“发布数据”示例，把消费者的 `acquire` 改成 `relaxed`；用 ThreadSanitizer 或代码推理说明哪里失去了同步。
3. 用 `compare_exchange_weak` 实现一个“只允许第一个线程成功”的 `try_claim()`。
4. 为一个包含余额和交易次数的类写出互斥锁版本，再解释为什么两个独立原子变量不足以保持一致。
5. 把 C++20 的 `state.wait()` 示例改为条件变量版本，比较两者适合的状态数量和等待条件。

完成后应能回答：

- 原子性、可见性和顺序分别解决什么问题？
- 为什么 `relaxed` 能安全做计数，却不能用来发布普通数据？
- `release`/`acquire` 如何建立 happens-before 关系？
- 为什么一个原子变量不能保护一个 `std::vector`？
- 什么时候应停止研究内存序，改用互斥锁？

## 速记

```text
一个独立值          -> std::atomic
计数/统计            -> 常可用 relaxed
发布数据             -> release store + acquire load
多个字段/复杂不变量 -> mutex
不确定内存序         -> 先用默认 seq_cst，再测量优化
volatile             -> 硬件/特殊信号，不是线程同步
```
